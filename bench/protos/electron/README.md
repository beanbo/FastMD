# FastMD — прототип на Electron

Настоящий Markdown-просмотрщик на Electron (класс Typora / Obsidian / MarkText), измеренный общим харнессом
`bench/harness/bench.py` по `bench/PROTOCOL.md`. Цель — найти самую быструю **честную** конфигурацию запуска для
этого стека и показать, куда уходит время.

## Итог в двух словах

* Лучший вариант `electron`: **~880–930 мс** до первого экрана (медиана, small/medium/large), окно видно через ~765 мс.
  Для сравнения: калибровочный `baseline-win32` — 70–90 мс, VS Code — ~1,5 с, Notepad — ~0,5 с.
* **~60 % времени (~480–570 мс) уходит ещё до первой инструкции приложения**: `CreateProcessW` для
  неподписанного `FastMD.exe` размером 246 МБ (Defender сканирует образ при каждом запуске). Изнутри приложения это
  не лечится.
* Всё, что после старта процесса (Node + Chromium + окно + рендерер + первая раскладка), — **~260–290 мс**, и в
  тюнинге выжато почти всё: осталось ~100 мс первой раскладки/кадра и ~120 мс неизбежной инициализации Chromium.
* Главный рабочий рычаг — **отключить GPU** (софтверный композитинг, без отдельного GPU-процесса): −65…−140 мс
  и −80 МБ commit. Остальные «ручки» дают единицы миллисекунд или находятся в пределах шума.
* Вывод для выбора стека: Electron упирается в пол **~0,85–0,9 с** на этой машине. «Как пуля» (<200 мс) он не
  откроется без резидентного процесса.

## Как собрать

```powershell
pwsh -File bench/protos/electron/build.ps1
```

* При отсутствии `node_modules` выполняет `npm ci` по `package-lock.json`, затем `node node_modules/electron/install.js`
  (в Electron ≥ 42 нет postinstall; zip-кэш — в `bench/.tools/electron/cache`, не в `%LOCALAPPDATA%`).
* Пересоздаёт `out/`: `out/FastMD/` — упакованное приложение (копия Electron dist, `electron.exe` → `FastMD.exe`,
  `resources/app/` = esbuild-бандл + page.html со встроенным CSS + koffi; `default_app.asar` удалён; из locales
  оставлены en-US и ru), `out/app-default/` — «обычная» папка приложения для варианта по умолчанию.
* Проверено с нуля: `npm ci` (14 с) + `build.ps1` (5 с). npm 11 предупреждает, что install-скрипты esbuild/koffi
  не выполнены (allow-scripts) — это не мешает: бинарники берутся из optional-зависимостей
  (`@esbuild/win32-x64`, `@koromix/koffi-win32-x64`).
* Профили Chromium создаются при первом запуске в `out/userdata-tuned/` и `out/userdata-default/` (вне `dist_dir`).

## Варианты (`proto.json`)

| id | Что это |
|---|---|
| **`electron`** (лучший) | Упакованное приложение `out/FastMD/FastMD.exe`; esbuild-бандл; без меню приложения; `app.disableHardwareAcceleration()` + `--disable-software-rasterizer` (софтверный композитинг, без GL/WARP) + `--in-process-gpu` (нет отдельного GPU-процесса); окно `show:false` → `loadFile()` (запуск рендерера) → `show()`; пока рендерер стартует, main читает и парсит только **первые ~4K символов** (до безопасной границы блока); рендерер забирает их через `ipcRenderer.invoke`, вставляет, двойной rAF → IPC → `DwmFlush()` → `t_content`. Остальное дописывается после первого кадра секциями с `content-visibility:auto`. Файлы > 256 КБ: до первого кадра читается только «голова» (256 КБ), хвост — после (если в первом куске есть возможная reference-ссылка `[x][id]`/`[id]`, файл читается целиком, чтобы найти определение). sandbox + contextIsolation включены. |
| `electron-gpu` | То же, но графика Chromium по умолчанию: аппаратное ускорение (ANGLE/D3D11) в отдельном GPU-процессе (`FASTMD_OPTS=gpu,gpuproc`). Показывает цену GPU-процесса на первом кадре. |
| `electron-default` | «Типичное Electron-приложение»: `electron.exe <папка>` (через `default_app.asar`), `require()` из node_modules, меню/GPU/webPreferences по умолчанию, весь документ парсится (с полным highlight.js) **до** создания окна, HTML пишется во временный файл → `loadFile()`, отчёт — когда первый экран постепенно парсящейся страницы попал в DOM, + двойной rAF (до аудита — после DOMContentLoaded, см. «Аудит»). |

Экспериментальные ручки остались в коде (`FASTMD_OPTS`: `gpu, gpuproc, swrast, nosandbox, single, netinproc,
noocclusion, menu, nohl, nochunk, chunk8k, worker, showfirst, datashell, mempart`; `scrollend` — отладка: после
досылки прокрутить в конец; `FASTMD_SWITCHES` — произвольные ключи Chromium), результаты — в разделе «Эксперименты».

### Честность измерения

* `t_content` берётся в main-процессе (он владеет окном) только после того, как рендерер вставил HTML в DOM и
  прошли **два requestAnimationFrame**, затем IPC `painted` → `DwmFlush()` (koffi) → метка. Раньше не метим.
* Первый экран — это реальный отрендеренный документ (заголовки, списки, код, таблицы по стилю), а не текст и не
  заглушка; 4096 символов прозы гарантированно больше одного экрана 1000×800 (≈ 37 строк). Досылка остального после
  первого кадра — легальная техника «первый вьюпорт первым» (PROTOCOL §3).
* Никаких резидентных процессов, кэшей отрендеренного HTML, встроенного корпуса. Дисковые кэши самого Chromium
  (профиль `userdata-*`) — штатное поведение любого Electron-приложения.
* Результат пишется атомарно (tmp + rename), затем `app.exit(0)`; харнесс видит чистый выход.

## Куда уходит время

1. **`CreateProcessW` ≈ 480–570 мс — больше половины.** `tools_createproc.py` мерит голый
   `CreateProcessW(CREATE_SUSPENDED)` + немедленный `TerminateProcess` (ни одна инструкция приложения не
   выполняется), 5 повторов, медианы:

   | exe | размер | подпись | CreateProcessW |
   |---|---|---|---|
   | `out/FastMD/FastMD.exe` (Electron 44) | 246 МБ | нет | **484 мс** |
   | `node_modules/electron/dist/electron.exe` | 246 МБ | нет | 535 мс |
   | Void.exe (VS Code fork) | 191 МБ | нет | 436 мс |
   | Cursor.exe (2.5.26) | 211 МБ | да (Anysphere) | 271 мс |
   | Code.exe (VS Code 1.113) | 203 МБ | да (Microsoft) | 252 мс |
   | `baseline-win32/out/baseline.exe` | 0,15 МБ | нет | 24 мс |

   Стоимость растёт с размером образа и примерно вдвое ниже у подписанных файлов — это on-access сканирование
   Defender (real-time protection включён; исключения без админа не добавить). Повторные запуски не кэшируются.
   Процессы-потомки (рендерер, network service, GPU) того же exe стартуют дёшево (~50–65 мс): образ уже
   отображён, пока жив browser-процесс. У Electron весь Chromium статически слинкован в один exe, поэтому
   уменьшить его нельзя без собственной сборки Electron.
2. **Инициализация Node + Chromium ≈ 115 мс** (`launch→main` 64 + `main→ready` 52) — фиксированная цена
   рантайма; наш код до `ready` — 16 мс (require electron, ключи, `nativeTheme`).
3. **Окно + рендерер ≈ 125 мс** (`ready→r_inserted`): конструктор окна 45 мс, старт процесса рендерера 64 мс.
   Парсинг Markdown (15–20 мс) полностью спрятан в это окно.
4. **Первая раскладка и кадр ≈ 90–100 мс** (`r_inserted→r_raf2`). В трассе Chromium (`results/traces/tuned_v2*`, более
   ранняя сборка того же варианта; трассировка сама замедляет) это `LocalFrameView::performLayout` ~118 мс, в основном шейпинг текста и загрузка шрифтов. Эксперимент
   (`results/exp13-fonts.json`, документы из `results/_exp/`): тот же medium без CJK+эмодзи — 75 мс, чистый
   ASCII — 68 мс. То есть **~25–30 мс — font fallback** (поиск и загрузка системных CJK- и emoji-шрифтов;
   в песочнице рендерера это синхронные IPC к font proxy в browser-процессе, в трассе видны `FontDataService::MatchFamilyName`), остальные ~65–70 мс — холодная инициализация Segoe UI Variable / Cascadia Mono,
   раскладка и растеризация.
5. **GPU-процесс = +100 мс на первом кадре** (`electron-gpu`: `r_inserted→r_raf2` 180–200 мс против 90–100),
   плюс +300 мс CPU и +80 МБ commit. Для текстового документа GPU-растеризация не нужна.
6. **Вариант по умолчанию** теряет на полном парсинге до окна (medium +145 мс, large +600 мс), полной
   раскладке всего документа (large: ~1 с между DOMContentLoaded и кадром) и на `default_app` (+20 мс).
   Большой документ (3,7 МБ) у него — 3,5 с и 1 ГБ commit, у тюнингованного — 0,93 с и 94 МБ. *(Аудит: 3,5 с —
   артефакт поздней метки; Chromium показывает первый экран, не дожидаясь конца парсинга, — реально ≈ 1,6–1,7 с,
   commit до `t_content` ≈ 420 МБ; полная раскладка всего документа (~1 с) идёт уже после первого экрана.)*

## Идеи дальнейшего ускорения

1. **Подписать exe сертификатом OV/EV.** По замерам подписанные файлы того же размера создаются примерно вдвое
   быстрее (Code.exe 203 МБ — 252 мс против 484 мс у нашего 246 МБ). Потенциально −200 мс, но **не проверено**
   на нашем exe (нужен настоящий сертификат).
2. **Уменьшить exe:** собственная сборка Electron без PDF, печати, spellchecker, WebGPU/Dawn, медиа — возможно
   −30…40 % размера → −100…150 мс сканирования. Цена — сборка Chromium (часы, ~100 ГБ).
3. **Резидентный режим (`electron-resident`):** скрытый процесс держит Chromium и образ exe в памяти, новое окно
   открывается за ~150–250 мс (окно 45 + рендерер ~60 + раскладка ~100). По протоколу допустим только как
   `-resident`; здесь не делался.
4. Первый кусок по **оценке высоты**, а не по 4K символов (у medium первый экран — ~1100 символов):
   −10…20 мс раскладки.
5. Font fallback (~25–30 мс) убрать честно нельзя — CJK/эмодзи стоят на первом экране; разве что прогревать
   DirectWrite-fallback в browser-процессе параллельно старту рендерера (не проверялось).
6. V8-снапшот для бандла main: бандл 225 КБ, выигрыш ≤ 10 мс.

Потолок для Electron на этой машине: ~480 мс (скан exe) + ~115 мс (Node+Chromium) + ~110 мс (окно+рендерер) +
~70 мс (раскладка) ≈ **0,78 с** без подписи; ~0,55–0,6 с с подписью — всё равно в 7–8 раз медленнее Win32-пола.

## Оценка трудозатрат на полный продукт

Electron — самый дешёвый в разработке вариант: вся экосистема markdown-it (сноски, якоря/оглавление, KaTeX,
Mermaid, GitHub alerts), поиск по странице Chromium, печать/PDF, темы на CSS.

* MVP-просмотрщик (этот прототип + ассоциация .md, single-instance, слежение за файлом, тёмная тема): **1–2 недели**.
* Полированный продукт (оглавление, поиск, настройки, math/mermaid, установщик electron-builder/NSIS,
  автообновление, **подпись кода**): **4–6 недель** одного разработчика.
* Цена: холодный старт ≥ 0,85–0,9 с, дистрибутив ~320 МБ распакованный (~100 МБ установщик), ~95 МБ commit на окно.
  Скорость «как пуля» этим стеком не достигается.

## Подводные камни

* **Electron ≥ 42 не скачивает бинарник в postinstall** — нужен явный `node node_modules/electron/install.js`
  (и `electron_config_cache`, чтобы кэш не уходил в профиль пользователя).
* npm 11 (`allow-scripts`) не запускает install-скрипты esbuild/koffi — работает за счёт prebuilt optional-deps.
* DwmFlush из Electron — только через нативный модуль/FFI (koffi, ~10 мс на загрузку): грузить лениво, пока идёт
  раскладка, иначе это на критическом пути.
* `app.disableHardwareAcceleration()` и ключи Chromium — строго до `ready`.
* `--single-process` в Electron 44 падает; `data:`-оболочка страницы медленнее `loadFile()`.
* С sandbox preload не может `require` произвольные модули — поэтому preload отдельный маленький файл, парсинг в main.
* `worker_threads` стоит ~35 мс на старте main — для маленьких документов это проигрыш.
* Первый запуск после установки/сборки — 1,2–3,4 с (Defender сканирует новый 246-МБ файл, холодный кэш).
* Профиль Chromium (~1,7 МБ, `Local State`, `Preferences`, кэши) создаётся при первом запуске; по умолчанию —
  `%APPDATA%\<name>`, здесь — `out/userdata-*` (правило «писать только в свою папку»).
* Картинки без известного размера дают «прыжок» раскладки после `t_content` — поэтому размер читается из заголовка.
* `content-visibility:auto` с постоянным `contain-intrinsic-size` (3000 px) делает полосу прокрутки неверной до
  раскладки секций: End / `scrollTo(конец)` на medium попадал в середину документа. Теперь высота каждой секции
  оценивается по исходнику (строки × 24 px × 1,4) — прокрутка в конец попадает точно.
* В `dist` лежат ненужные при софтверном рендере `dxcompiler.dll`, `dxil.dll`, `vk_swiftshader.dll`,
  `vulkan-1.dll`, `d3dcompiler_47.dll` (~38 МБ) и `LICENSES.chromium.html` (20 МБ) — в тюнингованном режиме они не
  грузятся (проверено по списку модулей), на время запуска не влияют; оставлены, т.к. общий dist с `electron-gpu`.

## Замечания к харнессу

Багов не найдено. Замечание: `launch_overhead_ms` (≈ `CreateProcessW`) для больших неподписанных exe — это
~60 % результата; при сравнении стеков его стоит показывать отдельной колонкой, иначе «медленный Electron» выглядит
как «медленный код», хотя код тут ни при чём.

## Аудит (независимая проверка, 2026-09-19)

Аудитор проверял прототип `electron` и `baselines-external` на честность метки `t_content` (PROTOCOL §3),
релизность сборки и качество рендера. Машина во время проверки была **нагружена** другими агентами — цифры грубые.

### Что проверено и подтверждено

* **Метки.** `t_content` берётся в main-процессе (владелец окна): рендерер получил первый кусок → `innerHTML` →
  rAF → rAF → IPC `painted` → `DwmFlush()` (koffi) → метка. Это ровно процедура §3 для веб-движков. Раньше
  «навигация началась / текст распарсен» метка не ставится.
* **Нет читов.** После прогонов не остаётся процессов FastMD/electron. Кэша отрендеренного документа нет: в
  `out/userdata-*` только служебные файлы Chromium (DIPS, Preferences, пустые GPUCache/Dawn*); `Code Cache` пуст (у
  страницы нет скриптов, CSP `default-src 'none'`). Корпус в сборку не встроен (`page.html` — только CSS, бандл —
  только код). `userdata-default/fastmd-doc.html` — временный HTML варианта default, перезаписывается при каждом
  запуске до `loadFile` (не кэш). Первый вьюпорт первым + досылка — разрешённая техника, в README описана.
* **Сборка.** `pwsh -File build.ps1` с нуля — OK: Electron 44.4.3 (релизный бинарник), JS — esbuild `--minify`.
* **Чанкинг корректен.** Новый `tools_audit_chunkcheck.js` сравнивает «первый кусок + досылка» с рендером **всего
  документа одним куском** (штатный `tools_headcheck.js` сравнивал только два способа нарезки между собой):
  small / medium / large — **IDENTICAL побайтно** (6 954 / 105 402 / 7 205 499 Б). Картинка первого куска:
  `file:///…/corpus/img/diagram1.png`, width/height 640×240 из заголовка PNG.
* **`bench.py check`** для `electron`, `electron-gpu`, `electron-default` на medium и large — CHECK OK без
  предупреждений; `observed_ms` на 15–30 мс **раньше** `window_ms` (харнесс видит окно ещё внутри `show()`).

### Независимо: документ действительно на экране в момент `t_content`? (`tools_audit_present.py`)

Инструмент запускает вариант как харнесс (Job Object, но `FASTMD_BENCH_EXIT=0`) и с появления окна непрерывно
снимает клиентскую область: `print` — `PrintWindow(PW_RENDERFULLCONTENT)` (собственная DWM-поверхность окна),
`screen` — `BitBlt` с экрана (то, что реально скомпоновал DWM). «Кадр с документом» — белый фон + текст. Шаг ~13–25
мс. Контроль на `baseline-win32` показал, что метод `screen` в первые ~180 мс искажается анимацией появления окна
(смешивание с тем, что под окном), поэтому для окна, показанного незадолго до контента, основной метод — `print`.

**Выводы.**
1. **`electron` (софтверный композитинг, основной вариант): метка честная** — документ появляется на экране в
   пределах разрешения снимков (≤ ~10 мс) от `t_content`.
2. **`electron-default` на large: метка была на ~2 с поздней.** Chromium парсит и рисует большой HTML
   постепенно: стилизованный первый экран на экране через ~1,7 с, а вариант ждал `DOMContentLoaded` (~3,4 с) —
   это не «первый экран документа» по §3. **Исправлено** (см. ниже).
3. **GPU-композитинг (`electron-gpu`, `electron-default`): процедура §3 (двойной rAF + `DwmFlush` в
   browser-процессе) срабатывает на ~40–90 мс РАНЬШЕ, чем кадр реально попадает на экран** (под нагрузкой).
   Кадр рисует и презентует отдельный GPU-процесс (DirectComposition) асинхронно; второй rAF означает лишь коммит
   предыдущего кадра, а `DwmFlush` в другом процессе его не дожидается. При софтверном композитинге in-process этого
   эффекта нет. **Не исправлялось в прототипе**: это свойство самой процедуры протокола, и оно, скорее всего,
   одинаково завышает скорость всех GPU-композитных веб-прототипов (WebView2 по умолчанию, Tauri/wry); правка только
   здесь сделала бы сравнение несимметричным. Рекомендация оркестратору — прогнать `tools_audit_present.py` (метод
   `print`) на других веб-вариантах или уточнить протокол (например, ждать presentation-feedback через
   `PerformanceObserver` paint/element timing). Для `electron-gpu`/`electron-default` реальное время ≈ число
   харнесса + 40–90 мс; вывод «GPU-процесс дороже софтверного композитинга» от этого только усиливается.
4. **`t_window` у всех Electron-вариантов** = событие `show`; до первого кадра рендерера клиентская область окна —
   системная подложка (бледный фон, не белый `backgroundColor`), т.е. отдельного кадра «фон нарисован» нет.
   `window_ms` здесь — «рамка окна видна», а не «окно что-то нарисовало». На `t_content` не влияет.

### Что изменено аудитором

1. `src/default/preload.js` — метка варианта `electron-default`: вместо `DOMContentLoaded` + двойной rAF теперь на
   каждом кадре проверяется, дотянулась ли уже распарсенная часть `<article>` до низа окна (или парсинг закончен);
   этот кадр рисует первый экран, следующий rAF → `painted`. Это та же процедура §3 («контент в DOM → двойной
   rAF»), применённая к первому экрану. Новая метка `r_viewport`.
2. `src/default/main.js` — koffi (для `DwmFlush`) грузится при `did-navigate`, пока рендерер парсит, а не синхронно
   после `painted`: ~15 мс инструментирования харнесса больше не записываются на счёт приложения (как уже было
   сделано в тюнингованном варианте). `r_raf2 → t_content`: ~20 → ~6 мс.
3. `proto.json` (notes `electron-default`), описание варианта и сноски в этом README; пересборка `build.ps1`.
4. Новые инструменты: `tools_audit_present.py`, `tools_audit_chunkcheck.js`.

Тюнингованный `electron` и `electron-gpu` не менялись.
