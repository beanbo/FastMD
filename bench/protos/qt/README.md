# FastMD — прототип `qt` (Qt 6.12 Widgets, C++)

**Итог:** Qt Widgets + `QTextBrowser`, в который md4c строит `QTextDocument` напрямую (без HTML/CSS), показывает
оформленный по спецификации документ за **~180–205 мс** медианы `t_content` (small/medium/large почти одинаково —
большой файл за счёт «сначала первый экран»). Пол этой машины — пустое Win32-окно `baseline-win32` — **~91 мс**
в тех же условиях, т.е. Qt добавляет **~90–110 мс**. Наивный Qt (`setMarkdown`, настройки по умолчанию) —
**650–1160 мс**. Лучший вариант `qt` — статически собранный Qt внутри DLL за маленькой exe-заглушкой; с официальными
DLL Qt (`qt-dll`) на 0–25 мс медленнее.

Все числа сняты на общей машине, где параллельно работали другие агенты (stdev 20–50 мс, единичные выбросы
до 2–3 с). Это грубое сравнение; финальный замер — за оркестратором.

## 2. Как собрать

```powershell
pwsh -File bench/protos/qt/build.ps1
```

Скрипт неинтерактивный и сам ставит всё нужное в `bench/.tools` (без админа):

1. Если нет Qt — venv `bench/.tools/aqt-venv` с aqtinstall (master) и fontTools, затем Qt 6.12.0 msvc2022_64
   (~1 мин загрузки) и исходники qtbase (~30 с).
2. `build/` → `out/`: CMake/Ninja против официальных DLL и `windeployqt` без переводов, software OpenGL,
   D3D/DXC-компиляторов, VC redist и плагинов imageformats/iconengines/generic/tls/networkinformation (PNG встроен в QtGui).
3. Если нет статического Qt — `build-qt-static.cmd` (configure + ninja + install; на 7950X ≈ 6 мин, 1438 шагов).
4. `build-static/` → `out-static/`: то же приложение как `fastmd_core.dll` (приложение + статический Qt) и
   крошечный `fastmd-qt-static.exe`, который только вызывает экспорт `fastmd_run()`.

Пересборка приложения при установленном Qt — 35–45 с. Скрипт чистит и пересоздаёт только свои папки (`build*`, `out*`).

Вспомогательное (в сборке не участвует):
- `tools/gen_coverage.py` — генерирует `src/fontcoverage.inc` (покрытие cmap шрифтов Windows 11; нужен fontTools);
- `tools/shot_scroll.py <variant> <doc> <px> <out.png>` — скриншот, прокрученный на N DIP;
- `tools/marks.py <run.json>` — медианы марок по варианту/документу;
- `tools/loadlog.ps1 -Doc large [-Exe …] [-Extra …]` — догрузка всего документа и максимальная пауза UI (§6).

## 3. Как устроено

```
main ─ fmb_init ─ QApplication ─ ReadFile(.md) ─ md4c(первые ~8 КБ) → QTextCursor → QTextDocument
     ─ MdView(QTextBrowser) ─ resize(1000×800) ─ setDocument ─ show ─ paintEvent ─ (queued) DwmFlush → t_content
     ─ после первого кадра: рабочий поток строит ВЕСЬ документ во втором QTextDocument
       → подмена через setDocument (позиция прокрутки сохраняется) → раскладка остатка шагами по ~16k символов
```

- **Без HTML-круга.** md4c-колбэки сразу создают блоки, символьные форматы, списки и таблицы через `QTextCursor`
  (`src/mdbuilder.cpp`). Никакого `setHtml`/CSS-парсера.
- **То, чего `QTextDocument` не умеет** (скругления, фон блока кода с паддингом, полоса цитаты, линия под h1/h2,
  скруглённый фон inline-кода, маркеры списков как у GitHub, зебра таблиц, `<hr>`), помечается флагами в
  `QTextBlock::userState()` и рисуется `MdView::paintDecorations` под текстом (`src/mdview.cpp`). Чекбоксы задач —
  свой `QTextObjectInterface`.
- **Свой фолбэк шрифтов** (`src/fontfallback.cpp`): текст режется на прогоны по скриптам, и каждому прогону явно
  назначается семейство (Segoe UI Variable / Segoe UI / Segoe UI Symbol / Segoe UI Emoji / Yu Gothic UI /
  Microsoft YaHei UI / Malgun Gothic) по заранее сгенерированным таблицам покрытия. Иначе Qt на первом же символе
  вне основного шрифта перебирает **все** ~350 установленных семейств (≈230 мс на этой машине, см. `qt-stock`).
- **Первый экран первым** (разрешено §3 протокола): если файл > 16 КБ, до первой отрисовки строится только кусок
  до первого ATX-заголовка после 8 КБ (граница всегда между блоками верхнего уровня и вне fenced-кода);
  определения ссылок `[x]: url` дописываются к каждому куску. `t_content` снимается по кадру, где первый экран
  уже **полностью оформлен**.
- **Догрузка остального** (после `t_content`; в бенч-режиме с выходом не выполняется): рабочий поток строит полный
  документ в отдельном `QTextDocument`, не прикреплённом к виджету (без раскладки, только md4c + вставки,
  ~0,17 мс/КБ), затем `moveToThread` в GUI-поток и подмена через `setDocument` с восстановлением прокрутки
  (проверено попиксельно: кадр при прокрутке 800 px совпадает с `qt-full`). Раскладку ниже экрана ведёт свой
  `LayoutDriver`: он глушит таймер ленивой раскладки Qt (тот удваивает шаг до 200 000 символов и замораживает UI
  на 0,5–0,7 с) и двигает раскладку сам шагами по ~16k символов, обновляя диапазон прокрутки после каждого шага.
  Для сравнения оставлены флаги `--slices` (старый способ: порции по 32 КБ прямо в показанный документ) и
  `--qtlazy` (штатная ленивая раскладка Qt).
- **Честная отметка `t_content`:** первый `MdView::paintEvent` → после возврата из paint (backing store уже сброшен
  в окно) через `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` вызывается `fmb_content_presented_ex()` =
  `DwmFlush()` + запись результата. `t_window` — момент того же первого paint.
- **Статика в DLL:** всё приложение + статический Qt лежат в `fastmd_core.dll` (`FASTMD_AS_DLL`, экспорт
  `fastmd_run`), exe — 107-КБ заглушка (`src/stub.cpp`). Редко нужные при старте системные DLL (d3d9/d3d11/d3d12/dxgi,
  UIAutomationCore, setupapi, comdlg32, winmm, ws2_32 и др.) подключены через `/DELAYLOAD`.
- DPI: манифест PerMonitorV2, окно 1000×800 DIP, заголовок `<file> — FastMD (<id>)`.

## 4. Варианты (`proto.json`)

| id | exe | Что это |
|---|---|---|
| **`qt`** (лучший) | `out-static/fastmd-qt-static.exe` | Статический Qt в `fastmd_core.dll` + 107-КБ заглушка, все ручки ниже. У предыдущего агента назывался `qt-sdll` (sdll = static-in-DLL) |
| `qt-dll` | `out/fastmd-qt.exe` | Тот же код и ручки, но с официальными DLL Qt (как собрал бы любой проект). Сборка Qt не нужна, дружит с LGPL. На 0–25 мс медленнее `qt` (у предыдущего агента это был вариант `qt`) |
| `qt-full` | `out-static/fastmd-qt-static.exe --chunk=0` | Как `qt`, но весь документ строится до первой отрисовки — показывает цену и пользу «первого экрана первым» |
| `qt-stock` | `out/fastmd-qt.exe --stock --window --ime` | Наивный Qt с официальными DLL: `QTextDocument::setMarkdown(..., MarkdownDialectGitHub)` (встроенный md4c-импортёр Qt), вид по умолчанию, весь документ, фолбэк шрифтов Qt, обычное `Qt::Window`, IME включён |

Машина: Ryzen 9 7950X, Windows 11 26200, Defender RTP включён, **параллельно работали другие агенты**.

до **2,5 с** (Defender сканирует новые exe/DLL).

### Догрузка всего документа (после `t_content`, не бенч-метка)

`pwsh -File tools/loadlog.ps1 -Doc large [-Exe out/fastmd-qt.exe] [-Extra --slices|--qtlazy|--chunk=0]` — окно
остаётся открытым, приложение пишет `FASTMD_QT_LOADLOG`: когда построен весь документ, когда закончена раскладка и
самая длинная пауза event loop за 10 с после первого кадра (таймер 2 мс). Время — от марки `main`:

| Способ (large, 3,7 МБ) | весь документ доступен | раскладка закончена | макс. пауза UI |
|---|---|---|---|

## 8. Идеи дальнейшего ускорения

1. **Параллельно с `QApplication` (~40 мс):** в фоновом потоке заранее создать DirectWrite font face'ы нужных
   шрифтов, прочитать файл, построить первый кусок (построению нужен только `QFont`) — потенциально −10…20 мс.
2. **Урезанная инициализация платформы** (статика это позволяет): патч плагина `qwindows` без clipboard viewer,
   power/theme-наблюдателей и запроса Advanced Color, плюс своя `QPlatformFontDatabase`, регистрирующая только
   7 используемых семейств вместо ~350 — оценочно −15…25 мс. Приватные API Qt.
3. **`QGuiApplication` + `QRasterWindow`** без QtWidgets и стилей, отрисовка `QTextDocument` напрямую через
   `QAbstractTextDocumentLayout::draw` — минус QtWidgets и создание стиля.
4. **Ещё меньше Qt** в статической сборке (`-no-feature-*` для неиспользуемых частей Gui/Widgets) — меньше образ,
   меньше статической инициализации.
5. **Раскладка больших документов** — узкое место уже после первого кадра: сама раскладка Qt для large занимает
   4,7–6 с (≈1,4 мс на 1000 символов). Сделанное (поток + подмена + `LayoutDriver`) убирает зависания, но не
   ускоряет. Дальше — виртуализация: несколько небольших `QTextDocument` по разделам и своя прокрутка с оценочной
   высотой.
6. **Резидентный режим** (`qt-resident`, §6 протокола): уже запущенный процесс получает путь по `WM_COPYDATA` —
   ожидаемо 40–70 мс. Не реализован.

## 9. Подводные камни

1. **aqtinstall 3.3.0 (PyPI) не ставит Qt 6.11+** — нужна ветка master с GitHub (в `build.ps1` так и сделано).
   Исходники 6.12.0 в репозитории лежат как `qtbase-everywhere-src-6.12.0-rc.zip` (в `.cmake.conf` —
   `PRERELEASE alpha1`), т.е. статический Qt формально собран не из того же снапшота, что официальные DLL.
2. **Фолбэк шрифтов Qt — главный тормоз наивного подхода:** первый же CJK-/эмодзи-символ заставляет Qt перебрать
   все установленные шрифты (≈230 мс). Свой itemizer это обходит, но `src/fontcoverage.inc` сгенерирован из шрифтов
   **этой** Windows 11; на другой сборке ОС покрытие может отличаться (некритично: незнакомый символ уходит в
   штатный фолбэк Qt).
3. **Скрытая GPU-проба Qt:** любое top-level окно типа `Qt::Window` грузит драйвер видеокарты через Direct3D9
   (~150 мс с RTX 5070). Отключается только сменой типа окна (`Qt::Dialog` + хинты кнопок); окно выглядит и
   ведёт себя как обычное.
4. **`QTextDocument` — не браузер:** нет скруглений, паддинга блоков, полос цитат, зебры — всё нарисовано вручную
   по флагам блоков. Семейство «Segoe UI Variable Text» в Qt имеет только Regular/Bold: semibold задаётся
   именованным экземпляром «… Semibold», а semibold-italic — через статический «Segoe UI Semibold».
5. **Ленивая раскладка `QTextDocumentLayout`** удваивает шаг от 1 000 до 200 000 символов каждые 10 мс
   (`QTextDocumentLayoutPrivate::layoutStep`), поэтому большой документ после показа замораживает UI на 0,5–0,7 с
   за шаг. Публичного API для шага нет; обход — фильтр событий таймера на объекте раскладки, свои мелкие шаги через
   `blockBoundingRect()` и ручной `documentSizeChanged` (QTextEdit сам экстраполирует высоту по `layoutStatus()`).
   Это опора на внутреннее поведение Qt — при обновлении Qt перепроверять. Дописывание в прикреплённый документ
   тоже дорого: каждая вставка вызывает `documentChanged` → раскладку до места вставки, поэтому полный документ
   строится отдельно и подменяется целиком.
6. **Баг, найденный при доводке:** `QAbstractTextDocumentLayout::hitTest(FuzzyHit)` для точки в верхнем поле
   страницы, пока ленивая раскладка не закончена, возвращал блок внутри ещё не спозиционированной таблицы далеко
   ниже экрана → у `qt-full` на medium первый кадр был без маркеров списков, линий под заголовками и фона
   inline-кода. Исправлено: у верха страницы декорации рисуются с первого блока, иначе hitTest — только подсказка
   с проверкой по `blockBoundingRect` (`MdView::paintDecorations`).
7. **Defender:** первый запуск после сборки — ~2,5 с; большой exe сканируется внутри `CreateProcess` (+35–40 мс на
   каждый запуск для exe на 21 МБ), поэтому статика вынесена в DLL за маленькой заглушкой.
8. **Межпрогонное влияние (важно для оркестратора):** после процесса, который перебрал все системные шрифты
   (`qt-stock`), **следующий** запуск любого варианта тратит на заполнение шрифтовой базы на 40–100 мс больше
   (шаг `parsed→view` 13 → 56…118 мс), и пауза 2 с между запусками не помогает (`results/order1.json`,
   `order3.json`, `pair-qt-t-stk.json`; для `--window`/`--ime` эффекта нет). Вероятно, дело в Windows Font Cache
   Service. При порядке `--order interleaved` (по умолчанию) вариант, идущий сразу за таким «шрифтожором»,
   штрафуется: в первом прогоне этой сессии статический вариант шёл после `qt-stock` и выглядел на 60–130 мс
   медленнее, чем есть. Рекомендация: мерить `qt-stock` (и похожие варианты других стеков) отдельно или с
   `--order grouped`.
9. **LGPL:** статическая линковка Qt требует дать пользователю возможность перелинковки (объектные файлы) или
   коммерческую лицензию. Если это неприемлемо — `qt-dll` (официальные DLL) медленнее всего на 0–25 мс.

### Найденное

1. **`qt-stock` портит замер следующего Qt-процесса (подтверждено).** В `results/audit-run.json` (interleaved;
   `qt` в каждом круге шёл сразу после `qt-stock`) шаг `parsed→view` у `qt` занял 45–147 мс, у всех остальных
   11–15 мс. Медианы `qt` 283,9/297,9 мс (small/medium) против 201,8/192,8 мс у **того же exe** в варианте `qt-full`.
   Эффект срабатывает один раз: страдает только первый Qt-процесс после `qt-stock`. Через 30 с он ещё держится
   (`view` 49,0 мс против 12,4–13,0). Не-Qt стеки не задеты: `cpp-d2d` после `qt-stock` 70,9 мс против 67,4 в
   контроле, `avalonia` 149,7 против 152,7. **Поэтому `qt-stock` исключён из финального набора.** Если нужен его
   ориентир, мерить его отдельной серией после всего остального. В `proto.json` он оставлен и помечен.
2. **Выигрыш статики (`qt`) над официальными DLL (`qt-dll`) не воспроизвёлся.** В чистых сериях без `qt-stock`:
   `qt` 155,7/172,8 мс, `qt-dll` 160,3/169,1 мс (`results/audit-run-nostock.json`), на medium 174,9 против 175,7
   (`results/audit-vs-baseline.json`). Разница не больше 5 мс в обе стороны, то есть в пределах шума. Реальные
   отличия только в peak commit (14 против 68 МБ) и размере поставки (20,1 против 26,8 МБ). Цифры §6 «−19/−26 мс»
   считать неподтверждёнными.
3. Честные ограничения, на `t_content` не влияют:
   - деление на куски опирается только на ATX-заголовки (`#`). Файл больше 16 КБ без `#`-заголовков после 8 КБ
     строится целиком, как в `qt-full` (~0,17 мс/КБ, то есть ~0,6 с на 3,7 МБ);
   - `ImmDisableIME(-1)` отключает IME на весь процесс. Для будущего поля поиска (CJK-ввод) его придётся вернуть;
   - `Qt::Dialog` вместо `Qt::Window` — обходной приём ради пропуска GPU-пробы Qt. Внешне окно обычное.
