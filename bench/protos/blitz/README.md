# blitz — FastMD на DioxusLabs Blitz (Stylo + Taffy + Parley + Vello)

Прототип «настоящего CSS без Chromium»: Markdown → HTML (comrak) → DOM (html5ever) → CSS (Stylo, движок
Firefox) → layout (Taffy) → текст (Parley/fontique/HarfRust) → растр (vello_cpu) → окно (winit + softbuffer).
Упаковка исследования `research/lab/blitz` (приложение `rdme`, см. `research/02-web-and-html-engines.md` §10)
в прототип на общем harness'е, с собственным конвейером запуска.

## Итог

| Вариант | small | medium | large | WS на t_content | dist |
|---|---|---|---|---|---|
| **`blitz`** (CPU-растр, первый экран чанком) | **110** | **121** | **116** | 33–50 MB | 8.0 MB, 1 файл |
| `blitz-full` (весь документ до первого кадра) | 114 | 121 | 2 654 | 33 MB … 776 MB | 〃 |
| `blitz-gpu` (vello_hybrid, wgpu DX12, RTX 5070) | 770 | 789 | 785 | 99–118 MB | 10.5 MB |
| для сравнения: `baseline-win32` (голое окно + GDI) | 75 | 76 | 74 | 14 MB | 0.15 MB |

t_content, мс, медиана 5 прогонов после первого (`bench.py run … --runs 5`, машина общая, см. «Быстрые замеры»).

- Исходный `rdme` из исследования давал 375–564 мс (CPU) и 1.2–1.5 с (GPU). Сейчас **~110–120 мс**, это
  **+35–45 мс к калибровочному полу** (голое Win32-окно). Из этой разницы ~18 мс — проверка Defender'ом 8-мегабайтного
  exe при `CreateProcess`, остальное — winit и первый кадр.
- Три главные находки, без которых больше ничего не помогало:
  1. **winit на Windows строит кэш раскладки клавиатуры синхронно внутри первого `ShowWindow`**
     (≈2 450 вызовов `ToUnicodeEx`, **150–350 мс** на этой машине). Исправлено патчем `vendor/winit-win32`.
  2. **Defender берёт ~2.2 мс на каждый МБ exe при каждом запуске.** Проверено опытом: +16 МБ нулей в конце
     `baseline.exe` дают +35 мс. Поэтому fat LTO + `opt-level="s"`: 17.7 → 8.0 МБ, launch −25 мс, t_content
     −25…−40 мс (попарные прогоны).
  3. **Конвейер по потокам.** UI-поток занят только окном, остальное параллельно: шрифты DirectWrite, парсинг,
     DOM и стили/раскладка первого экрана. Документ готов за ~30 мс до того, как окно готово его принять.
- Большой документ: первый экран — первые ~12 КБ markdown (тот же документ, не заглушка). Затем в фоне
  собирается 256 КБ (готово через ~0.2–0.3 с), потом полный документ (через ~2.5–4 с). Каждая стадия
  подменяется с сохранением прокрутки. Узкое место — не старт, а **стоимость кадра на огромном DOM**:
  3.7 МБ markdown дают ~100–140 мс на кадр, то есть прокрутка «large» дёргается (см. «Грабли»).
- Качество вёрстки: это настоящий CSS (`bench/common/style.css` + 3 правила-обхода, см. ниже), поэтому
  внешний вид почти один в один совпадает со спецификацией. Цветные эмодзи, CJK, кириллица, таблицы с
  выравниванием и «зеброй», картинки. Нет подсветки синтаксиса.

## Как собрать

```
pwsh -File bench/protos/blitz/build.ps1          # ~4 мин инкрементально, ~8–10 мин с нуля
pwsh -File bench/protos/blitz/build.ps1 -Clean   # cargo clean + полная сборка
```

- Нужны Rust stable (msvc) и MSVC Build Tools. Крейты берутся с crates.io по `app/Cargo.lock` (`--locked`).
  Blitz подключён path-зависимостями к `research/lab/blitz/src`. Если чекаута нет, `build.ps1` клонирует
  DioxusLabs/blitz на коммит `e7bf7bca` туда же.
- Target dir: `bench/.tools/blitz/target` (~3 ГБ, вне каталога прототипа).
- Профиль `dist`: fat LTO, 1 CGU, `panic=abort`, `opt-level="s"`, а горячие крейты (`vello_cpu`,
  `vello_common`, `fearless_simd`, `taffy`, `harfrust`, `skrifa`) собраны с `opt-level=3`, как в профиле `tiny`
  самого Blitz. В `app/.cargo/config.toml`: статический CRT и `/DELAYLOAD` для shell32/ole32/oleaut32/dwrite.
- Результат: `out/cpu/fastmd-blitz.exe` (варианты `blitz`, `blitz-full`) и `out/gpu/fastmd-blitz-gpu.exe`
  (`blitz-gpu`). Это один файл без DLL, рядом ничего не нужно.

Структура:

```
app/Cargo.toml, Cargo.lock, .cargo/config.toml
app/src/main.rs     конвейер запуска, приложение поверх blitz-shell, клавиатурная прокрутка
app/src/md.rs       comrak (GFM) -> HTML, обёртка страницы + style.css, нарезка первого экрана
app/src/net.rs      FileNet (картинки с диска), ExternalLinks (ShellExecuteW)
app/src/fmb.rs      протокол bench (метки, DwmFlush, ws_bytes, атомарная запись результата)
app/src/bin/showprobe.rs   проба стоимости ShowWindow в winit (feature "probe", в dist не входит)
vendor/winit-win32  winit-win32 0.31.0-beta.3 + патч (см. «Грабли»)
experiments/        сырые json замеров опытов, devlog-*.txt, showprobe.log, marks.py, pad_exe.py
results/quick-run.json   финальный быстрый прогон
shots/              скриншоты (bench.py shot)
```

## Как устроен запуск

```
t=0 CreateProcess ─ ~40 мс (из них ~18 мс Defender на 8 МБ exe) ─ main (~50 мс)
UI-поток:   EventLoop (17) ─ CreateWindowExW, скрытое, с пустым документом-заглушкой (15)
            ─ ShowWindow + активация (21) ─ забрать готовый документ (0 мс ожидания)
            ─ softbuffer resume (2) ─ первый кадр: paint_scene + vello_cpu + GDI present (9.5) ─ DwmFlush (5.6) = t_content
поток font: DirectWrite: коллекция системных шрифтов fontique + семейства из style.css (~13 мс)
поток doc:  чтение .md (1) ─ первые ~12 КБ до пустой строки вне ```-блока ─ comrak (1) ─ ждёт шрифты
            ─ DOM html5ever (2) ─ Stylo + Taffy + Parley для предсказанного вьюпорта (9) ─ готов на ~74 мс
поток rest: comrak → DOM → стили/раскладка сначала 256 КБ, потом всего документа → подмена (прокрутка сохраняется)
после кадра: фоновый прогрев кэша раскладки клавиатуры winit (патч), чтобы не тормозило первое нажатие
```

Цифры в скобках — медианы для medium из `results/quick-run.json`.

- Документ строится и раскладывается не в UI-потоке, а потом передаётся туда. `HtmlDocument` не `Send` только из-за
  двух trait-объектов без `Send` (`FontMetricsProvider` в Stylo, `HtmlParserProvider` в Blitz). Обёртка
  `SendDoc` с `unsafe impl Send` и обоснованием в `main.rs`: за ними стоят потокобезопасные типы, владение
  передаётся один раз.
- Вьюпорт для раскладки заранее предсказывается по `GetDpiForSystem` (1000×800 DIP). Если окно открылось на
  мониторе с другим DPI, `View::init` выставит настоящий, и Blitz перераскладывает.
- `View::init` / `resume` из blitz-shell вызываются вручную (как в `BlitzApplication::can_create_surfaces`,
  только по шагам): так можно поставить метки и подложить готовый документ через `replace_document`.
- Протокол (`fmb.rs`): `t_content` берётся после `present` первого кадра с документом (softbuffer:
  `SetDIBitsToDevice`/`BitBlt`; GPU: wgpu present) и `DwmFlush`. Кадр ловится в `ResumeReady`→`complete_resume`
  или в `RedrawRequested`, смотря что было раньше, и только при активном рендерере. `t_window` — тот же
  present: до него окно ничего не рисует. `ws_bytes` = `K32GetProcessMemoryInfo`. Выход — `exit(0)` сразу
  после атомарной записи json.
- Честность: резидентных процессов и кэшей нет. Коллекция шрифтов строится при каждом старте, корпус
  читается с диска, первый экран — настоящее начало документа, отрисованное тем же движком. Если
  доскроллить до конца чанка раньше подмены, там будет «…».

## Варианты (`proto.json`)

| id | exe / аргументы | Что это |
|---|---|---|
| `blitz` | `out/cpu/fastmd-blitz.exe --variant blitz` | Лучшая конфигурация: CPU-растр, ранний показ окна, первый экран чанком 12 КБ, стадии 256 КБ → весь документ в фоне, dist-профиль |
| `blitz-full` | тот же exe, `--full` | Весь документ до первого кадра, без чанков. Для документов >256 КБ стили считаются параллельно (Stylo `Parallel`) |
| `blitz-gpu` | `out/gpu/fastmd-blitz-gpu.exe`, env `WGPU_BACKEND=dx12`, `WGPU_POWER_PREF=high` | vello_hybrid на wgpu, тот же конвейер |

Ключи командной строки (для опытов; по умолчанию стоит лучшее): `--chunk <байт>` (12288), `--stage <байт>`
(262144, `0` = без промежуточной стадии), `--full`, `--late-window` (окно после готовности документа),
`--kbd-prewarm start|after|off` (after), `--dnd` (OLE drag&drop winit, выкл.), `--bg-seq` (фоновый документ без
параллельного Stylo), `--scroll-y <px>` (только для осмотра скриншотами). Переменная `FASTMD_BLITZ_LOG=<файл>`
пишет в файл тайминги фоновых стадий и кадров после `t_content`. В протоколе она не участвует.

## Что поддерживается (против §5 PROTOCOL)

| Элемент | Статус |
|---|---|
| Окно | PMv2 DPI (API до всего остального), клиент 1000×800 DIP, светлая тема (принудительно), заголовок `<файл> — FastMD (<вариант>)`, активируется |
| Заголовки h1–h6 | да, размеры и полужирный по спеке, у h1/h2 линия снизу, h6 серый |
| Абзацы, перенос по словам | да (Parley, ICU line breaking) |
| **bold** / *italic* / `code` / ~~strike~~ / ссылки | да. Курсив набран Segoe UI (у Segoe UI Variable нет italic, см. «Грабли») |
| Списки: маркированные, нумерованные, вложенные, задачи | да. Чекбоксы задач синие. Они не `disabled`, так что клик, видимо, переключает галочку (только на экране, файл не меняется; руками не проверял) |
| Цитаты, горизонтальная линия | да |
| Блоки кода | да: Cascadia Mono 13.5 px, фон `#f6f8fa`, радиус 6, отступ 16, **без переноса** (`white-space:pre`, `overflow:auto`; горизонтальную прокрутку длинных строк внутри блока руками не проверял) |
| Таблицы GFM | да: границы, полужирная шапка, «зебра», выравнивание колонок. `display:table` вместо GitHub-овского `display:block`, поэтому широкая таблица не прокручивается горизонтально |
| Картинки (локальные PNG/JPEG) | да, асинхронно через `FileNet`: могут появиться кадром позже, с перераскладкой |
| Подсветка синтаксиса | **нет** |
| Unicode | кириллица, CJK (fallback через DirectWrite), цветные эмодзи (Segoe UI Emoji) — да |
| Прокрутка | колесо, overlay-скроллбар (Blitz). Клавиши PageUp/PageDown/Space/стрелки/Home/End — свой обработчик, в Blitz этого нет |
| Масштаб | Ctrl+= / Ctrl+− / Ctrl+0 (blitz-shell) |
| Ссылки | http(s)/mailto открываются в браузере по умолчанию. `#якоря` и относительные .md не обрабатываются |
| Выделение и копирование текста | в Blitz есть (`clipboard` включён), подробно не проверялось |
| Тёмная тема, поиск, печать, TOC | нет |

Правила поверх `style.css` (`BLITZ_CSS` в `app/src/md.rs`, все обходят особенности Blitz):
`table{display:table;width:auto}`, `em,i{font-family:"Segoe UI"…}`, цвет и сдвиг чекбоксов задач.
Из HTML comrak'а убирается `disabled=""` у чекбоксов и завершающий `\n` в `<pre><code>`.

## Где время

Для medium ~120 мс против 76 у голого окна:

1. **~40 мс до `ResumeThread`** (у baseline 22). Разница почти целиком из-за размера exe: Defender проверяет
   файл при каждом `CreateProcess`. Опыт `experiments/pad_exe.py` (baseline + 16 МБ нулей в overlay, который даже
   не отображается в память): launch 26 → 62 мс, t_content 98 → 126 мс. Отсюда ~2.2 мс/МБ, для 8 МБ это ~18 мс.
2. **~10 мс загрузчик/CRT** до `main` (статический CRT и delay-load заметного выигрыша не дали, см. опыты).
3. **UI-поток, ~53 мс чистого winit/ОС.** EventLoop 17 мс: первая GUI-инициализация потока, скрытое
   окно-приёмник, TSF/IME, raw input. Создание окна 15 мс. ShowWindow с активацией 21 мс: TSF, DWM; голое
   окно по пробам `rust-webview` активируется за 30–45 мс. Всё это последовательно и зависит только от окна.
   У `baseline-win32` путь от `main` до `t_content` ~43 мс, у нас ~71 мс.
4. **Первый кадр ~9.5 мс**: `complete_resume` (новый `RenderContext` vello_cpu, пул на 8 потоков), `paint_scene`,
   растр 1000×800, перестановка байтов RGBA→BGRX и `SetDIBitsToDevice`. Потом **DwmFlush ~5.6 мс**, это
   требование протокола.
5. **Движок не на критическом пути.** Шрифты (13 мс), comrak (1 мс), DOM (2 мс), стили и раскладка первого
   экрана (9 мс) считаются в других потоках и готовы на ~74 мс, за 29 мс до того, как окно готово.
   Поэтому `blitz-full` на medium не медленнее `blitz`: даже весь документ (54 КБ, ~25 мс) успевает. Чанки
   нужны для больших файлов.
6. **GPU**: `wgpu::Instance` со всеми бэкендами ~315 мс (грузятся Vulkan/GL ICD двух видеокарт). С
   `WGPU_BACKEND=dx12` ~20 мс. Дальше ~640–700 мс на D3D12-устройство и пайплайны/шейдеры vello_hybrid внутри
   `resume`. Для старта GPU-растр проигрывает в 6–7 раз.

## Идеи дальнейшего ускорения

- **Свой Win32-хост вместо winit.** blitz-shell тонкий, нужны окно, softbuffer-поверхность и перевод
  мыши/клавиатуры/колеса в события Blitz, ~1.5–2 KLOC. У голого окна от `main` до `t_content` ~43 мс, у нас
  ~71 мс, из них ~15 мс кадр+DwmFlush и ~50 мс winit/ОС. Ожидаю −10…−20 мс.
- **Подпись кода и репутация.** Возможно, снимет часть проверки Defender при каждом запуске (здесь проверить нельзя).
  Сжатие exe (UPX) не поможет: AV распаковывает, плюс распаковка на старте.
- Ещё уменьшить exe: без jpeg, pulldown-cmark вместо comrak, отказ от `image`. Порядка −1…−2 МБ, то есть −2…−4 мс.
- Не пересоздавать `RenderContext` vello_cpu в `resume` и `complete_resume` (в `anyrender_vello_cpu` это
  каждый раз новый пул потоков). Около −1…−2 мс.
- **Большие документы:** виртуализация, то есть держать в DOM только окрестность вьюпорта (секции по заголовкам)
  и дописывать мутатором DOM вместо полной пересборки. Сейчас Blitz на каждом кадре обходит всё дерево.
- GPU только после первого кадра: первый кадр CPU-растром, `wgpu`-устройство и пайплайны vello_hybrid греются
  в фоне и подхватываются для плавной прокрутки на 4K (как `rust-gpu-egui-softfirst`). Нужен форк
  `anyrender_vello_hybrid` (сейчас нет API подложить готовый `WGPUContext`/устройство).
- Резидентный режим (`-resident`) убрал бы ~50 мс процесса и EventLoop, но это другой класс решения.

## Оценка трудозатрат до продукта

MVP-читалка на этом стеке: **5–7 недель** одного разработчика, плюс постоянная поддержка форков.

- 1 неделя: ассоциация `.md`, один экземпляр, drag&drop, перечитывание при изменении файла (`notify`),
  якоря и относительные ссылки, настройки, установщик.
- 1–1.5 недели: подсветка синтаксиса (syntect/tree-sitter → классы в HTML), тёмная тема (CSS), поиск по
  странице (API поиска в Blitz нет: свой проход по тексту DOM и подсветка), проверка выделения и копирования,
  печать/PDF (в Blitz печати нет, нужен свой экспорт).
- 1–2 недели: виртуализация больших документов (см. выше). Без неё файлы >1 МБ прокручиваются рывками.
- 1 неделя: свой Win32-хост или сопровождение патча winit, accessibility (AccessKit в Blitz есть, в прототипе
  выключен).
- Риски: Blitz в beta (API меняется от коммита к коммиту, фиксировать ревизию), три локальных обхода
  (`SendDoc`, патч winit, CSS-обходы). JS нет, поэтому Mermaid/KaTeX только нативными средствами или через
  MathML/SVG. Память на огромных документах: ~0.8 ГБ WS на 3.7 МБ markdown.

## Грабли

1. **winit (и tao) на Windows: 150–350 мс в первом `ShowWindow`.** На `WM_SETFOCUS` вызываются
   `update_modifiers` → `LAYOUT_CACHE.get_agnostic_mods()` и `synthesize_kbd_state` →
   `get_current_layout()`. Оба строят кэш раскладки: 16 состояний модификаторов × 256 VK через `ToUnicodeEx`.
   На этой машине (ru+en) вызов стоит 60–140 мкс. Патч `vendor/winit-win32` (4 места, помечены
   `FastMD patch`):
   - `get_agnostic_mods` строит кэш, только если нажат правый Alt;
   - `synthesize_kbd_state` берёт HKL через `GetKeyboardLayout(0)`;
   - `WM_INPUTLANGCHANGE` прогревает кэш в фоне;
   - публичная `prewarm_keyboard_layout(thread_id)` вызывается в фоне после первого кадра.
   То же самое нашёл прототип `rust-webview` для tao.
2. **Размер exe = время запуска** (Defender, ~2.2 мс/МБ, см. опыт с overlay). Отсюда fat LTO + opt-s.
   LTO-сборка идёт ~2.5 мин на вариант.
3. **`HtmlDocument` не `Send`**, хотя по факту потокобезопасен. Нужна обёртка `SendDoc` (`unsafe impl Send`).
   Правильное исправление — `Send`-границы у `FontMetricsProvider`/`HtmlParserProvider` в апстриме.
4. **`DocumentConfig.ua_stylesheets` заменяет стандартный UA-лист**, а `HtmlDocument::from_html` дописывает
   `DEFAULT_CSS` в конец, и тот перебивает правила той же специфичности. Поэтому `style.css` вставлен как
   авторский `<style>` в `<head>`, как и требует протокол.
5. **`display:block` у таблицы** (GitHub-стиль в `style.css`): Blitz не строит анонимную табличную обёртку и
   сваливает все строки в одну. Нужен `display:table`, так же поступает upstream `rdme`.
6. **У Segoe UI Variable Text нет italic**, а синтетический наклон Parley/Vello даёт битые глифы
   («ıtalıc»). Курсив набирается Segoe UI.
7. Чекбоксы: у `disabled` цвет зашит светло-серым, `vertical-align:middle` игнорируется. Поэтому снят
   `disabled`, задан `color` и сдвиг вниз.
8. blitz-shell рисует первый кадр в `complete_resume` по событию `ResumeReady`, а не в `RedrawRequested`.
   Метка «первый `RedrawRequested`» в исследовательском `fmb.rs` могла сработать на другом кадре. Здесь
   проверяются оба пути, и только при активном рендерере.
9. Параллельный обход Stylo нельзя запускать для двух документов одновременно (blitz #430). Поэтому
   `Parallel` только у финального фонового документа (и у `--full` для больших файлов), а первый экран и
   промежуточная стадия `Sequential`.
10. Прокрутки с клавиатуры в Blitz нет, пришлось писать свою. Знак `scroll_viewport_by` как у колеса:
    положительный — вверх.
11. **Стоимость кадра растёт с размером DOM**: medium ~8 мс, стадия 256 КБ ~11–13 мс, полный large ~100–140 мс
    (resolve обходит дерево ~99 мс даже без изменений, paint ~40 мс; `experiments/devlog-frames.txt`).
12. GPU: без `WGPU_BACKEND=dx12` wgpu поднимает Vulkan/GL-драйверы обеих видеокарт (~300 мс).
    `WGPU_POWER_PREF=low` (AMD iGPU) медленнее RTX на ~200 мс.
13. Шум общей машины: одиночные запуски гуляют ±30–50 мс, первый запуск нового exe стоит +250–350 мс (Defender
    сканирует впервые). Сравнивать только чередующимися прогонами.

### Замечания, не влияющие на честность

1. `check_presented` проверяет только `renderer.is_active()`, а не факт отрисовки кадра. Теоретически метку
   можно взять без кадра в двух случаях: (а) `View::redraw` пропускает кадр при
   `has_pending_critical_resources`, а это бывает только у `<link rel=stylesheet>` в `<head>`, которого в нашей
   странице нет; (б) `vello_hybrid` пропускает кадр при ошибке `get_current_texture`. На корпусе ни то ни другое
   не происходит: скриншоты и `observed` согласованы. Не исправлял, потому что без форка anyrender не узнать,
   отрисован ли кадр.
2. UX: в классе окна winit `hbrBackground = null`, окно видно раньше первого кадра, поэтому клиентская область
   ~35 мс не нарисована. Продукту стоит показывать окно в `complete_resume` или залить фон.
3. Чанк первого экрана отличается от начала полного документа только в редких случаях: ссылки-сноски и
   reference-ссылки, определённые ниже чанка (в корпусе их нет), и «рыхлость» списка, если разрез пришёлся внутрь
   loose-списка.
4. `blitz-gpu` рабочий, но неконкурентный (~790 мс). Оставлен в финальном замере как опорная точка GPU-растра.

### Подозрение на баг harness'а (сообщено оркестратору, harness не трогал)

`run_once` пишет результат в `bench/results/tmp/<variant id>.json`, а это имя общее для всех параллельных
вызовов harness'а. Если два агента одновременно гоняют один и тот же вариант, один читает результат другого. Так
случилось в моём прогоне: baseline-win32/medium #2 дал `content 2.67 мс`, `main −36.5 мс`, `window −2.6 мс`, окно
не наблюдалось. `run` не отбраковывает такие записи, в отличие от `check`, который предупреждает о метках вне
`[0, t_content]`. Предложение: уникальное имя файла на запуск (pid/uuid) и отбраковка записей с отрицательными
метками или без `observed_ms` в режиме `self`. На финальный последовательный замер это не влияет.
