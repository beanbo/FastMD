# wpf — C# .NET 8 WPF + Markdig → FlowDocument

Прототип FastMD на WPF: Markdig разбирает Markdown, собственный билдер строит `FlowDocument`
(заголовки, списки, чекбоксы, цитаты, таблицы с рамками и «зеброй», код с подсветкой, картинки),
документ показывается в `FlowDocumentScrollViewer`. Никакого XAML/BAML: весь UI собран в коде.

**Итог (медианы, пул 2 × 5 прогонов на шумной машине):** лучший вариант `wpf` показывает первый экран
за **~310–330 мс** (small 321 / medium 308 / large 329). Тот же код рендера со «стандартным» WPF-стартом
(`wpf-plain`) — **~505–530 мс**. Главные находки:

1. **Render-поток WPF стартует ~150 мс.** Внутри он загружает D3D9-драйвер видеокарты: на этой машине
   это 147 МБ DLL NVIDIA, и загружаются они даже в software-режиме. Этот старт идёт в отдельном потоке
   параллельно со всем остальным: −140 мс.
2. **Нативный лаунчер** начинает загрузку этого драйвера в первую миллисекунду процесса, ещё до старта .NET,
   а затем поднимает .NET в том же процессе через `hostfxr`: ещё −60 мс.
3. Без темы Aero2 (шаблоны в коде), без IME, с прогревом шрифтов в фоне и software-рендерингом первого кадра:
   ещё −100 мс в сумме. **Сразу после первого кадра окно переключается на GPU.** Если оставить software-рендеринг,
   прокрутка развёрнутого на широкий монитор окна проседает до ~30 fps.

Нижняя граница стека на этой машине — около 300 мс. Для сравнения, `baseline-win32` показывает 70–90 мс.

## Сборка

```powershell
pwsh -File bench/protos/wpf/build.ps1               # r2r + лаунчер, jit, sc-r2r
pwsh -File bench/protos/wpf/build.ps1 -Experiments  # + sc-single и r2r-icu (только для таблицы ручек)
pwsh -File bench/protos/wpf/build.ps1 -Only r2r     # одна сборка (r2r собирает и лаунчер)
```

С нуля всё собирается за 10–40 с. Скрипт чистит только свои каталоги (`out/`, `src/obj`, `src/bin`) через
`[IO.Directory]::Delete` с проверкой, что путь внутри папки прототипа. Каждая сборка идёт со своими
`obj/<flavor>` / `bin/<flavor>`. Лаунчер собирается `launcher/build-launcher.cmd` через `bench/tools/msvc.cmd`,
с тем же `app.manifest`, что и у .NET-приложения (PerMonitorV2).

| Сборка (`out/…`) | Параметры | Размер `dist_dir` |
|---|---|---|
| `r2r` | framework-dependent, `PublishReadyToRun=true` (FastMdWpf.dll + Markdig.dll) + `fastmd-wpf.exe` | 1.75 МБ |
| `jit` | framework-dependent, чистый IL (то, что даёт `dotnet publish` по умолчанию) | 0.67 МБ |
| `sc-r2r` | self-contained папка, всё R2R | 145.7 МБ |
| `sc-single` (эксп.) | self-contained single-file, R2R, без сжатия | 155.3 МБ |
| `r2r-icu` (эксп.) | как `r2r`, но `InvariantGlobalization=false` | 1.62 МБ |

Общие runtime-настройки (csproj): `InvariantGlobalization=true` + `PredefinedCulturesOnly=false`
(иначе WPF падает на `CultureInfo("en-US")`), `TieredPGO=false`, `ConcurrentGarbageCollection=false`
(нет фонового потока GC), `UseSystemResourceKeys=true`, `SatelliteResourceLanguages=en`.
Манифест: PerMonitorV2, supportedOS Windows 10/11.

## Варианты (`proto.json`)

| id | exe | Аргументы | Что это |
|---|---|---|---|
| **`wpf`** | `out/r2r/fastmd-wpf.exe` (лаунчер) | — | лучшая честная конфигурация: лаунчер с предзагрузкой GPU-драйвера, R2R framework-dependent, все ручки ниже включены; первый кадр в software, дальше GPU |
| `wpf-hw` | `out/r2r/fastmd-wpf.exe` | `--hw` | то же, но GPU-рендеринг с самого первого кадра (D3D9) |
| `wpf-apphost` | `out/r2r/FastMdWpf.exe` | — | те же ручки, но стандартный .NET apphost: чистый .NET без нативного кода |
| `wpf-plain` | `out/jit/FastMdWpf.exe` | `--plain` | точка отсчёта: «учебный» старт WPF — apphost, IL/JIT, тема Aero2, IME, GPU, всё последовательно (код рендера тот же) |

Все ручки — аргументы командной строки. По умолчанию включена лучшая конфигурация, так что при двойном
клике приложение ведёт себя как `wpf`.

| Ключ (по умолчанию → выключить) | Где | Что делает |
|---|---|---|
| D3D-предзагрузка → `--no-d3d-prewarm` | лаунчер | в первую миллисекунду процесса отдельный поток делает `Direct3DCreate9Ex` и для каждого адаптера `GetAdapterIdentifier`, `GetDeviceCaps(HAL)`, `CheckDeviceType`. Это грузит `d3d9.dll` и user-mode-драйвер GPU. Объект `IDirect3D9Ex` живёт до конца процесса, чтобы DLL драйвера не выгрузились. Main-поток тем временем запускает .NET через `hostfxr_main_startupinfo`, как это делает стандартный apphost |
| `--sw` → `--hw` | .NET | `RenderOptions.ProcessRenderMode = SoftwareOnly` на время старта: первый кадр рендерится в DIB, render-потоку не нужно D3D9Ex-устройство и swap chain на критическом пути |
| `--gpu-later` → `--sw-only` | .NET | (при `--sw`) сразу после `t_content` `ProcessRenderMode = Default` и `HwndTarget.RenderMode` пересчитывается: окно переходит на GPU. Устройство создаётся уже после первого кадра |
| `--warm` → `--no-warm` | .NET | второй STA-поток в начале `Main` создаёт свой `Dispatcher` и `MediaContext`. Это запускает процесс-глобальный render-поток WPF параллельно с загрузкой типов и сборкой документа в главном потоке |
| `--warm-text` → `--no-warm-text` | .NET | третий поток форматирует первые 4 КБ файла через `FormattedText` (обычный / semibold / bold / italic / моноширинный). Так шрифты, CJK- и emoji-fallback и LineServices попадают в общие кеши WPF |
| `--lean` → `--theme` | .NET | `OverridesDefaultStyle` + шаблоны Window / FlowDocumentScrollViewer / ScrollViewer через `FrameworkElementFactory` и свой тонкий скроллбар. Словарь темы Aero2 (BAML) не грузится до первого кадра |
| `--no-ime` → `--ime` | .NET | `InputMethod.IsInputMethodEnabled=false`: при первом `WM_SETFOCUS` не регистрируется TSF text store (~20 мс). В читалке нет ввода текста |
| `--plain` | .NET | = `--hw --no-warm --no-warm-text --theme --ime` |
| эксперименты | .NET | `--full` (весь документ до первого кадра), `--prelayout` / `--pretemplate` (layout или шаблоны до `Show()`), `--first=N` (сколько оценочных экранов строить до первого кадра, по умолчанию 2), `--early-hwnd`, `--app` (с объектом `Application`), `--scroll=N` (прокрутка после первого кадра, для скриншотов), `--scrolltest[=max]` (тест плавности прокрутки, см. ниже) |

Независимо от ключей всегда работают:
- чтение и разбор Markdig в отдельном потоке, параллельно со стартом WPF;
- **сначала первый экран**: до первого кадра строятся блоки на ≥2 оценочных экрана. Оценка высоты
  заведомо занижена, поэтому экран всегда заполнен; для medium это 16 из 391 блока. Остальное дописывается
  секциями на приоритете `Background` после `t_content`, размер секций растёт от 64 до 4096 блоков.
  Файлы больше 96 КБ до первого кадра разбираются только до ~24 КБ (разрез по ATX-заголовку вне fenced-кода),
  полный разбор идёт в фоне. Это разрешено протоколом (§3);
- картинки первого экрана декодируются в потоке разбора: замороженный `BitmapImage` из `FileStream`.

`t_content` = `Window.ContentRendered` → колбэк `Dispatcher` на приоритете `Background` → `DwmFlush()`,
строго по PROTOCOL §3. `t_window` в WPF совпадает с первым кадром, в котором уже есть документ.
Никакого кеша между запусками и резидентных процессов нет. Все «прогревы» — это параллельная
работа внутри одного запуска.

### Плавность прокрутки: почему после первого кадра нужен GPU

`--scrolltest[=max]` после построения всего документа прокручивает на 40 DIP за кадр и пишет интервалы между
кадрами (`CompositionTarget.Rendering`) в `trace.log`: `pwsh -File tools/trace-run.ps1 -Doc medium -Extra '--scrolltest=max'`.
Монитор здесь ~160 Гц, развёрнутое окно — 3456×1408 DIP.

| Режим | окно 1000×800: p50 / p95, мс | развёрнутое 3456×1408: p50 / p95, мс |

| software весь сеанс (`--sw-only`) | 12.1 / 15.3 (~80 fps) | **31–32 / 35–37 (~30 fps)** |

## Куда уходит время

Источники: профиль `dotnet-trace` (`runs/prof/*.speedscope.json`, `tools/speedscope_top.py`), список модулей процесса
(`tools/modules.ps1`) и отметки.

1. **Процесс и .NET до `Main`: ~80 мс.** Нативный baseline успевает за это время открыть окно целиком.
   R2R, self-contained и лаунчер эту часть не меняют. Single-file делает хуже: +330 мс.
2. **Render-поток WPF: ~150 мс без лаунчера.** При первом `MediaContext` WPF синхронно ждёт
   (`DUCE.Channel.SyncFlush`), пока композитор создаст display set: `d3d9.dll`, перечисление адаптеров
   (здесь их два: RTX 5070 и AMD iGPU), user-mode-драйвер NVIDIA. В процессе оказываются смаплены
   **`nvgpucomp64.dll` 106 МБ + `nvd3dumx.dll` 41 МБ** и `D3DCompiler_47_cor3.dll`, причём **и в software-режиме**.
   Кроме того, в процесс инжектятся `RTSSHooks64.dll` (RivaTuner) и Windhawk: это окружение машины.
   Прототип борется с этим двумя способами: `--warm` запускает этот старт вторым потоком из `Main`,
   а лаунчер грузит драйвер ещё до .NET. С лаунчером render-поток готов на ~162 мс вместо ~240.
3. **GPU-устройство окна (~50–80 мс, только `--hw`).** После создания HWND render-поток создаёт D3D9Ex-устройство
   и swap chain. С лаунчером и без него это частично перекрывается с measure, отсюда разница `--hw`/`--sw` 10–40 мс.
   В `wpf` устройство создаётся уже после `t_content`, при переключении на GPU.
4. **Главный поток — теперь он критический путь (~225 мс после `Main`):** cctor-ы WPF и `Dispatcher` ~45–65;
   `FlowDocument` ~15; `HwndSource` / `HwndTarget` ~40, внутри в том числе регистрация stylus (WISP),
   `RegisterDropTarget` (OLE) и `WTSQuerySessionInformation`; шаблон FDSV + `AttachTextEditor` → контексты PTS/LineServices
   плюс форматирование первых 16 блоков ~41; arrange ~11; ShowWindow, активация и первый `Rendering` ~27; кадр ~10;
   Background + DwmFlush ~12. Что уже снято ручками: тема Aero2 — словарь BAML 25–30 мс, стиль Window 15–20,
   шаблон FDSV 15, `EnsureResourceChangeListener` ~10; шрифты и fallback ~15; TSF 20–30; декодирование картинки
   с urlmon ~27.

## Идеи дальнейшего ускорения

1. **Главный поток WPF — последний крупный кусок (~225 мс после `Main`).** Реалистичные резервы:
   - отключить stylus/touch (`Switch.System.Windows.Input.Stylus.DisableStylusAndTouchSupport`): ~5 мс, но пропадёт тач-прокрутка;
   - убрать `FlowDocumentScrollViewer`/`TextEditor` с первого экрана: рисовать первый экран напрямую
     (`DrawingVisual` + `GlyphRun`/`FormattedText`), FlowDocument подставить позже. Это ~40–60 мс, но нужна своя вёрстка,
     и в этой точке WPF как стек теряет смысл.
2. Лаунчер мог бы заранее подгружать и другие тяжёлые DLL. Проверено на своих native-DLL WPF (`wpfgfx_cor3`,
   `PresentationNative_cor3`, `D3DCompiler_47_cor3`): эффекта нет, убрано.
3. Виртуализация для больших файлов (по элементу на блок в виртуализирующей панели или свой layout). Для продукта обязательна.
4. Composite R2R, `DOTNET_TC_*`: ожидаемый эффект меньше 10–20 мс. Tiered/PGO/ICU уже измерены, это единицы–десятки мс.
5. Резидентный процесс (`-resident`) убрал бы ~80 + 150 мс, но это отдельная категория по протоколу.
6. NativeAOT и trimming для WPF официально не поддерживаются (COM, BAML, рефлексия), это тупик.

| Функции читалки: поиск, масштаб, тёмная тема, настройки, перезагрузка при изменении файла, печать, ассоциация `.md`, история | 2–3 недели |

Старт останется в районе **300–350 мс** на этой машине, в 3–4 раза медленнее нативного Win32/D2D.

параллельно. На машине с другой видеокартой вклад драйвера будет другим. Типографика хорошая (DirectWrite,
ClearType, настоящие таблицы), но emoji монохромные, а на больших файлах FlowDocument работает медленно.

## Грабли (что стоит знать)

- **`CompositionTarget.Rendering +=` создаёт `MediaContext`**, а с ним ~150 мс синхронного старта render-потока.
  Подписка в конструкторе окна просто переносит эту стоимость в другое место. Для отметок подписываться
  только после `SourceInitialized`.
- **Даже `RenderMode.SoftwareOnly` загружает D3D9 и драйвер GPU:** display set WPF перечисляет адаптеры всегда.
- **Software-рендеринг — только для первого кадра.** На развёрнутом 3440-px окне прокрутка в SW идёт ~30 fps.
  `RenderOptions.ProcessRenderMode` можно вернуть в `Default` во время работы. Чтобы окно пересчитало режим,
  `HwndTarget.RenderMode` нужно «передёрнуть» (SoftwareOnly → Default): пока процесс в SW, окно не выйдет из него
  само даже с `RenderMode.Default`.
- **Markdig `Descendants<LinkInline>()` на `ParagraphBlock` молча возвращает пусто**: метод обходит только
  `ContainerBlock` и `ContainerInline`. Из-за этого у предыдущего агента предекод картинок не работал,
  и декодирование (с urlmon) шло в UI-потоке, ~27 мс.
- `BitmapImage.UriSource` для локального файла вызывает `MapUrlToZone` (urlmon, ~14 мс при первом вызове),
  `StreamSource` из `FileStream` этого не делает.
- **`OverridesDefaultStyle` на TextElement-ах** экономит загрузку словаря темы (~20 мс), но у классов `Bold` и `Italic`
  жирность и курсив задаёт именно тема. С ODS они становятся обычным текстом, поэтому здесь используются `Span` с явным
  `FontWeight`/`FontStyle`. `Hyperlink` также берёт из темы курсор и цвета. Ставить ODS нужно в инициализаторе,
  до добавления первого ребёнка: добавление ребёнка «инициализирует» элемент и запускает поиск стиля
  (`new TableCell(para)` уже поздно).
- Тему Aero2 грузит любой элемент с `DefaultStyleKey`: Window, FDSV, ScrollBar, Hyperlink, Run, Paragraph…
  Один забытый элемент — и словарь всё равно загружен.
- Прогревать тему во втором потоке (`new Window()` + FDSV там) **медленнее**: главный поток ждёт блокировки
  cctor и словарей (505 против 460 мс). В параллель стоит выносить только то, что не пересекается по блокировкам.
- `--prelayout` (measure до `Show()`) ничего не даёт. Arrange создаёт визуалы и всё равно ждёт `MediaContext`,
  а в `--hw` создание D3D-устройства окна перестаёт перекрываться с measure и уходит на критический путь (471 против 377 мс).
- Лаунчер: DPI-awareness берётся из манифеста **exe процесса**, поэтому `app.manifest` встроен и в `fastmd-wpf.exe`.
  `[STAThread]` у `Main` работает и при хостинге через `hostfxr_main_startupinfo`, если поток лаунчера
  не инициализировал COM раньше. Поток предзагрузки COM не трогает.
- `InvariantGlobalization=true` без `PredefinedCulturesOnly=false` роняет WPF: шрифтовой код создаёт `CultureInfo("en-US")`.
- Замеры сильно шумят: по машине параллельно гоняются чужие прототипы, разброс медиан между проходами 20–60 мс.
- **Harness.** `bench.py run all` запускает варианты **всех** прототипов, а не только своего (я так по ошибке
  запустил чужие приложения). Если exe чужого варианта пропадает посреди прогона (его пересобирают), `run`
  падает с `FileNotFoundError`: `resolve_exe()` в `run_once` вызывается вне `try`, и результаты всего прогона теряются.
- Safety-хук: удаление каталогов в `build.ps1` сделано через `[System.IO.Directory]::Delete($p, $true)`.

### Оговорки для сравнения (не нарушают протокол)

1. **large.md: окно почти не отвечает ~10 с после первого кадра.** Остаток дописывается 9.4 с (`tools/trace-run.ps1`).
   Всё это время UI-поток занят. Проверка пингом `WM_NULL` через `SendMessageTimeout` каждые 5 мс в течение 12 с:
   31 пауза длиннее 50 мс, в сумме 11.8 с, самая длинная **1.09 с**. Выше в README сказано «может подтормаживать»,
   на деле это фриз с паузами до секунды. По §3 дописывать остаток после первого экрана можно, но `t_content` для
   large показывает время до первого экрана, а не до момента, когда с документом можно работать.
   Для medium за первые 0.3 с после `t_content` было 3 паузы, самая длинная 126 мс (переключение на GPU и дописывание),
   дальше окно отвечает сразу.
2. **Нативный лаунчер** с предзагрузкой драйвера GPU — законный приём в рамках одного запуска. Выигрыш (~60 мс)
   зависит от видеодрайвера машины (здесь NVIDIA, 147 МБ user-mode DLL). Он же добавляет +54 МБ к peak commit.
3. `wpf-plain` — не «голый» WPF. Он тоже разбирает файл в отдельном потоке и строит сначала первый экран.
   Отличаются только ручки старта: тема, IME, GPU, IL/JIT, без параллельных прогревов.
