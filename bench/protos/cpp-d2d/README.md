# cpp-d2d — C++20 · raw Win32 · DirectWrite (+Direct2D) · md4c

Прототип FastMD на «голом» Win32 с собственным рендерером Markdown поверх DirectWrite.
Кандидат «максимальная скорость».

## TL;DR

* **Лучший честный вариант `cpp-d2d`**: DirectWrite растеризует глифы прямо в GDI DIB (без Direct2D/Direct3D и без
  загрузки GPU-драйвера), первый экран разбирается, раскладывается и рисуется на рабочем потоке *параллельно* с
  созданием окна. На шумной машине (другие агенты грузили CPU на 55–65 %) медиана `t_content` составила
  **≈ 64–80 мс** для small/medium/large. В тех же условиях `baseline-win32` (пустое окно + одна строка GDI) показал
  96.8 мс, а `cpp-d2d` 81.2 мс: прототип **быстрее калибровочного «пола»**.
* Весь критический путь приходится на ОС: CreateProcess, загрузчик, CreateWindowEx, ShowWindow и DwmFlush. Сам
  конвейер документа (чтение, md4c, DirectWrite, раскладка, рендер) занимает ~10–15 мс и полностью прячется за
  созданием окна.
* **GPU здесь только мешает.** Создание аппаратного D3D11-устройства на RTX 5070 стоит ≈ 200 мс, а на iGPU дорог
  swap chain (дисплей подключён к dGPU). `cpp-d2d-gpu` даёт ≈ 300–400 мс, WARP (программный D3D) — ≈ 100–140 мс.
* **`cpp-d2d-resident`** (заранее запущенный процесс, со стартом «с нуля» напрямую не сравнивается): **≈ 30–42 мс**.
  Сюда входит полный запуск второго процесса `fastmd-d2d.exe --forward`, который передаёт путь резиденту.
* Качество: GitHub-подобная типографика по спецификации PROTOCOL §5, цветные emoji, CJK, таблицы с зеброй, чекбоксы,
  подсветка синтаксиса (16 языков), локальные картинки через WIC.

| Картинки | WIC (через `CoCreateInstance`) на фоновом потоке после первого кадра; размеры PNG/JPEG/GIF берутся из заголовка файла ещё до декодирования |

Больше зависимостей нет: ни vcpkg, ни NuGet, ни runtime.

## Сборка

```
pwsh -File bench/protos/cpp-d2d/build.ps1        # ~20 с, неинтерактивно, с нуля
```

Скрипт удаляет `out/`, `out-resident/` и `obj/`, затем собирает `md4c.c` (C, UTF-16) и шесть `.cpp` и линкует
`out/fastmd-d2d.exe`. Этот же файл копируется в `out-resident/fastmd-d2d.exe` (зачем — см. раздел «Resident»).
Экспериментальный `obj/fastmd-open.exe` в варианты не входит. Компилятор вызывается через
`bench/tools/msvc.cmd`, поэтому PATH от Developer Prompt не нужен.

## Архитектура старта

```
UI-поток   : fmb_init → SetProcessDpiAwarenessContext(PMv2) → разбор argv → старт doc-потока
             → ImmDisableIME(0) → RegisterClassEx → CreateWindowEx (+DWMWA_TRANSITIONS_FORCEDISABLED)
             → ShowWindow → первый WM_PAINT: join(doc) → BitBlt готового кадра → EndPaint → DwmFlush → t_content
doc-поток  : ReadFile → UTF-8→UTF-16 → md4c → плоская модель (blocks + inline runs)
             → DWriteCreateFactory + 8 IDWriteTextFormat → оценка высот всех блоков
             → IDWriteTextLayout только для блоков ПЕРВОГО ЭКРАНА → рендер кадра в DIB (back-end gdi)
dev-поток  : (только dxgi/hwnd) D3D11CreateDevice + D2D device/context
после кадра: N потоков (до 8, BELOW_NORMAL) считают точные высоты остальных блоков → точный scroll extent;
             WIC-декодирование картинок; для больших файлов подмена префиксной модели на полную
```

* **Модель документа**: плоские массивы `Block` (текст, код, hr, таблица, картинка; отступ, вертикальный зазор,
  маркер списка/чекбокса, приглушённый цвет) и `Run` (bold/italic/code/strike/link + цвет). Весь текст — одна
  `std::wstring`. На текстовый блок — один `IDWriteTextLayout`, на таблицу — сетка layout'ов (по одному на ячейку).
* **Виртуализация (first-viewport-first)**: до первого кадра раскладываются только видимые блоки (в medium это
  21 из 679). Для остальных высота сначала оценивается (для кода и hr считается точно, для картинок — по заголовку
  файла), а после первого кадра уточняется фоновыми потоками. При этом верхний видимый блок «заякорен», поэтому
  страница не прыгает. Это разрешённый протоколом приём (PROTOCOL §3), и `t_content` честный: первый экран на
  момент метки полностью и окончательно отрисован.
* **Префиксный разбор больших файлов** (> 256 KB): для первого экрана md4c разбирает префикс ≥ 48 K символов до
  ближайшего заголовка верхнего уровня вне fenced-кода, поэтому блоки получаются те же самые. Полный разбор
  параллельно идёт на своём потоке, и полная модель подменяет префиксную сразу после первого кадра.
* **Back-end `gdi`**: `IDWriteBitmapRenderTarget` рисует глифы (ClearType/grayscale, как настроено в системе) в
  DIB. Цветные emoji рисуются послойно (COLR) через `TranslateColorGlyphRun`, потому что
  `IDWriteBitmapRenderTarget3::DrawGlyphRunWithColorSupport` на Win11 26200 отсутствует. Скруглённые
  прямоугольники, круги и галочки чекбоксов рисует маленький SDF-растеризатор с антиалиасингом. В окно кадр
  попадает одним `BitBlt`.
* Прокрутка колесом анимирована (сглаживание), есть клавиатура (↑↓, PgUp/PgDn/Space, Home/End, Esc/Ctrl+W —
  закрыть). Scrollbar свой: overlay, «горячий» при наведении, drag ползунка, клик по треку. Ссылки подсвечиваются
  курсором-рукой и по клику открываются в браузере (`ShellExecute`). Изменение размера окна вызывает перераскладку
  с якорем, `WM_DPICHANGED` обрабатывается.

## Варианты (`proto.json`)

| id | exe / args | Что это |
|---|---|---|
| **`cpp-d2d`** (лучший) | `out/fastmd-d2d.exe --backend=gdi --no-ime --no-anim` | DirectWrite → GDI DIB. Кадр готов на doc-потоке ещё до ShowWindow. IME на UI-потоке отключён, DWM-анимация открытия отключена |
| `cpp-d2d-warp` | `--backend=dxgi --warp --no-ime --no-anim` | Direct2D DeviceContext на D3D11 **WARP** (CPU) + flip swap chain; устройство создаётся на dev-потоке |
| `cpp-d2d-gpu` | `--backend=dxgi --no-ime --no-anim` | «Классический» Direct2D на аппаратном D3D11 (адаптер по умолчанию = RTX 5070) + flip swap chain |
| `cpp-d2d-resident` | `out-resident/fastmd-d2d.exe --forward`; резидент: `out-resident/fastmd-d2d.exe --resident --backend=gdi --no-ime --no-anim` | **RESIDENT.** Процесс запущен заранее (PROTOCOL §6), новый экземпляр передаёт ему путь через `WM_COPYDATA` и выходит |

Id `cpp-d2d-exp`, `cpp-d2d-shot`, `cpp-d2d-trace` встречаются только в dev-скриптах `tools/`. Вариант с
отдельным launcher'ом (`fastmd-open.exe`) в `proto.json` не вошёл: он медленнее, см. раздел «Resident».

### Ключи командной строки (для экспериментов)

| Ключ | Действие |
|---|---|
| `--backend=gdi\|dxgi\|hwnd\|dcrt` | back-end (по умолчанию `dxgi`) |
| `--warp` / `--igpu` | для `dxgi`: WARP-устройство / аппаратное устройство на адаптере `MINIMUM_POWER` (AMD iGPU) |
| `--no-ime` | `ImmDisableIME(0)` для UI-потока (в читалке на этом потоке нет ввода текста) |
| `--no-anim` | `DWMWA_TRANSITIONS_FORCEDISABLED`: окно появляется сразу с полной непрозрачностью, без fade/zoom |
| `--serial` | всё на UI-потоке, без рабочих потоков (для сравнения) |
| `--no-virt` | раскладывать весь документ до первого кадра |
| `--no-prefix` | не использовать префиксный разбор больших файлов |
| `--show-late` | показывать окно только после готовности первого кадра |
| `--signed-only` | `ProcessSignaturePolicy MicrosoftSignedOnly` (блокирует внедряемые чужие DLL) |
| `--trace` | журнал загрузок DLL, первых оконных сообщений и марок → `%TEMP%\fastmd-d2d-trace.txt` |
| `--scroll-test=N` | после первого кадра отрисовать N кадров прокрутки, статистика → `%TEMP%\fastmd-d2d-scroll.txt` |
| `--scroll=Y`, `--size=WxH`, `--show-cmd=N` | отладка: начальная прокрутка, размер клиентской области в DIP, команда ShowWindow |
| `--resident` / `--forward` / `--no-preshow` | резидентный режим / передать документ резиденту, если он запущен / не держать запасное окно показанным (cloaked) |
| `--id=<variant>` | id варианта для заголовка окна |

## Resident: что сделано и что выяснилось

`fastmd-d2d.exe --resident` при старте прогревает всё, что не зависит от документа: DirectWrite factory и форматы,
font fallback, кэш глифов (прогоняет через полный конвейер образец с кириллицей, CJK, emoji, кодом и таблицей),
GDI-холст и класс окна. Ещё он создаёт **запасное окно документа**, показывает его, но держит DWM-cloaked, так что
окно не композитится, не видно пользователю и harness'у (`list_windows` пропускает cloaked). Сам резидент
слушает message-only окно `FastMDd2dResident`.

`fastmd-d2d.exe --forward <file>`, если резидент найден, отправляет ему `WM_COPYDATA` (путь,
`FASTMD_BENCH_OUT/EXIT`, свою метку `main`) и выходит. Если резидента нет, это обычный холодный старт. Резидент
запускает doc-поток и активирует запасное окно (`SetForegroundWindow` ≈ 8 мс идёт параллельно doc-потоку). Кадр
кладётся в ещё cloaked окно, окно раскрывается (uncloak), затем DwmFlush и `t_content`. После записи результата
окно документа закрывается, а в простое готовится новое запасное (PROTOCOL §6).

Результаты A/B (`tools/exp_launcher.py`, medium, n = 9):

* **Отдельный крошечный launcher оказался медленнее.** `fastmd-open.exe` (4 KB, без CRT, только kernel32 и user32)
  дал 84.4 мс, а `fastmd-d2d.exe --forward` — 66.1 мс. Разница целиком в CreateProcess: 38 мс против 7.5 мс.
  Пока файл exe отображён живым процессом (резидентом), его image section уже существует, и новый процесс из
  **того же файла** создаётся в разы быстрее. Варианты launcher'а с манифестом (UAC, supportedOS) и со
  статическим CRT разницы не дали. Поэтому launcher оставлен только экспериментом (`src/launcher.cpp`,
  собирается в `obj/`).
* **Запасное окно, заранее показанное cloaked**, дало 34.5 мс против 41.7 мс со скрытым окном: дорогой первый
  ShowWindow уходит в простой.
* Ранний `SetForegroundWindow` (до кадра, пока окно cloaked) в одиночных разбивках убирает ≈ 5 мс с критического
  пути, но по медиане 9 запусков это в пределах шума.
* **Гигиена замера:** резидент и «холодные» варианты используют **разные копии** exe (`out-resident/` и `out/`).
  Иначе живой резидент ускорял бы CreateProcess холодных вариантов на ≈ 15 мс (см. ниже).

## Замечания к harness (для оркестратора)

1. **`bench.py run` держит все резиденты живыми всё время прогона.** Любой холодный вариант, чей exe — тот же
   файл, что и у резидента, получает «тёплый» CreateProcess. Измерено здесь: `launch_overhead` 6 мс против 20–25
   мс, `main` на 7–15 мс раньше. В первом быстром прогоне (`results/quick-run-1.json`, резидент ещё на
   `out/fastmd-d2d.exe`) холодный `cpp-d2d` из-за этого выглядел на ≈ 10–15 мс быстрее. В этом прототипе
   исправлено отдельной копией exe. Другим прототипам с `-resident` стоит проверить то же самое, а harness мог бы
   запускать резиденты только на время своих вариантов.
2. `observed_ms` обычно на 6–10 мс раньше `t_content`: observer видит окно видимым до DwmFlush. Это ожидаемо.
3. На этой машине работает RivaTuner Statistics Server (`RTSS.exe`), и его `RTSSHooks64.dll` внедряется в каждый
   GUI-процесс на первом CreateWindowEx (≈ 10 мс). Это общий налог для всех прототипов, включая baseline.

## Идеи дальнейшего ускорения

* Холодный старт: внутри приложения резервов практически нет (< 2 мс: UI-поток от `main` до ShowWindow занят
  только вызовами ОС, а конвейер документа и так идёт параллельно). Существенное лежит вне приложения:
  * подпись exe (Authenticode) и репутация SmartScreen/Defender могут удешевить скан при CreateProcess (не проверялось);
  * без RTSS и прочих глобальных хуков CreateWindowEx станет на ≈ 10 мс быстрее.
* Резидент: общий процесс для всех окон (без CreateProcess совсем) возможен только через shell-расширение или
  DDE/COM-активацию, а это уже архитектура продукта. Альтернатива — «tray-резидент» с автозапуском, это ровно
  вариант `-resident`.
* Большие документы: подготовка раскладки без `IDWriteTextLayout` (свой line breaker поверх `IDWriteTextAnalyzer`)
  ускорила бы фоновое измерение высот (сейчас ≈ 0.6 с на 3.7 MB). Кэш высот по хэшу файла ускорил бы повторные
  открытия.
* Картинки: декодировать только видимые и с даунскейлом (`IWICBitmapScaler`) — меньше памяти на больших документах.

## Оценка трудозатрат на полноценный продукт

Одному опытному C++/Win32-разработчику, опираясь на этот прототип:

* **MVP-читалка** (выделение и копирование, поиск Ctrl+F, масштаб, тёмная тема, reload при изменении файла,
  якоря и оглавление, горизонтальная прокрутка кода и таблиц, настройки, ассоциация `.md`, инсталлятор/MSIX,
  подпись): **≈ 6–8 недель**. Самое трудоёмкое — выделение текста поверх per-block `IDWriteTextLayout` (hit-testing
  между блоками и ячейками) и поиск с подсветкой.
* **Полноценный продукт** (UI Automation text pattern для скринридеров, печать и PDF, удалённые картинки, нормальная
  подсветка вроде tree-sitter, сноски или другой парсер, HTML-подмножество, математика, mermaid): ещё
  **≈ 3–4 месяца**. Математика и mermaid без веб-движка — самые рискованные пункты.

Главный риск стека: всё, что в браузере даётся бесплатно (выделение, доступность, HTML, математика), здесь пишется
руками.

## Подводные камни (найдено по ходу)

* `IDWriteBitmapRenderTarget3::DrawGlyphRunWithColorSupport` на Win11 26200 недоступен (QI не проходит). Цветные
  emoji на GDI-back-end'е рисуются вручную послойно (COLRv0 через `TranslateColorGlyphRun`).
* DIB у `IDWriteBitmapRenderTarget` top-down, хотя `GetObject` возвращает положительную высоту. Ориентация
  определяется пробой пикселя через `SetPixelV`.
* md4c 0.5.3 в UTF-16-режиме не собирается или работает неверно без правки `_T("*_~")` (см. «Стек»).
* Аппаратный D3D11 на этой машине стоит ≈ 200 мс: две видеокарты, загрузка UMD NVIDIA. Swap chain для окна на
  дисплее dGPU, созданный с iGPU-устройства, тоже ≈ 190 мс. Для «мгновенного» окна GPU противопоказан.
* `ImmDisableIME(0)` действует на поток и выигрывает ≈ 10 мс. Но в продукте с полем поиска IME понадобится: поле
  ввода нужно держать на отдельном потоке или создавать его окно лениво в другом потоке.
* Без `DWMWA_TRANSITIONS_FORCEDISABLED` метка не меняется, но пользователь видит fade-in. Для ощущения скорости
  флаг важен.
* Резидент: см. эффект одного файла exe (image section) и выгоду от заранее показанного cloaked-окна.
  `SetForegroundWindow` из фонового запуска может не активировать окно (foreground lock). Поэтому передающий
  процесс вызывает `AllowSetForegroundWindow(pid резидента)`.
* На больших файлах без виртуализации DirectWrite-раскладка всего документа занимает ≈ 1.8 с: виртуализация
  обязательна.

### Замечания (не исправлялись)

* **«Быстрее калибровочного пола» — в пределах шума.** В аудите `cpp-d2d` против `baseline-win32` дал 86.5 против
  90.5 мс (medium, n = 8 interleaved, `results/audit-vs-baseline.json`). Корректнее говорить «на уровне пола».
  Часть выигрыша даёт `--no-ime` (≈ 10 мс), которого у baseline нет. В продукте IME нужен для поля поиска, а
  `ImmDisableIME(0)` действует на весь поток, поэтому поле поиска придётся вынести в отдельный UI-поток. Это честная
  прикладная техника, но в сравнении её стоит учитывать.
* Картинка в первом экране была бы показана как плейсхолдер: место под неё резервируется, а декодирование идёт
  после кадра. На корпус не влияет. Веб-движки ведут себя так же.
* Префиксный разбор (large, > 256 KB): link reference definitions, объявленные ниже точки разреза, в первом кадре
  не применятся (по CommonMark они действуют на весь документ). На корпусе не проявляется, первый кадр совпадает с
  установившимся.
* `/GS-` (без проверок буфера) допустимо для бенчмарка. На старт влияет ничтожно, в продукте флаг нужно вернуть.
* Горизонтальной прокрутки у кода и таблиц нет, длинные строки обрезаются. Это задокументировано.

### Для оркестратора (harness)

* `bench.py run` поднимает **все** резиденты в начале и держит их до конца прогона. В этом прототипе эффект
  «тёплого» image section закрыт копией exe. Но при `run all` резиденты других прототипов (например, WebView2)
  держат прогретым общий runtime для их cold-вариантов. Рекомендация: `-resident`-варианты мерить отдельным `run`.
* `observed_ms` отражает только видимость окна, а не контент. Для проверки «контент на экране» можно использовать
  `tools/audit_onscreen.py` из этого прототипа.

### Оценка

* Визуальное качество **9/10**, полнота **9/10**. Типографика, отступы, заголовки h1–h6 с линиями, списки с
  маркерами по уровням, чекбоксы, цитаты, таблицы (выравнивание, зебра, семибольд-шапка), подсветка кода в палитре
  GitHub, цветные emoji, CJK, кириллица и картинки практически совпадают с эталоном `cpp-webview2` (тот же
  `style.css` в Chromium). По мелочи: hr 2 px (у GitHub 4 px), нет сносок и HTML, нет горизонтальной прокрутки
  кода и таблиц. Скриншоты аудита: `shots/audit-*.png`. Back-end'ы отличаются менее чем на 0.06 % пикселей
  (сглаживание), резидент совпадает с cold попиксельно.
* **Для финального замера пригодны все 4 варианта:** `cpp-d2d`, `cpp-d2d-warp`, `cpp-d2d-gpu`,
