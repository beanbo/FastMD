# litehtml-sciter — «лёгкие HTML-движки» для FastMD

Два прототипа одного вопроса: можно ли взять готовую HTML/CSS-вёрстку (и общий `bench/common/style.css`), но без
веса и старта WebView2/Chromium?

* **(b) litehtml 0.10 + свой `document_container` на Direct2D/DirectWrite** (C++20, CMake + Ninja) — основной вариант.
* **(a) Sciter.JS 6.0.5.0 + тонкий C++-хост** (sciter.dll).

Markdown в обоих случаях переводится в HTML через **md4c-html 0.5.3** (GFM: таблицы, зачёркивание, task lists,
autolinks); страница = `style.css` (вшит в exe при сборке) + несколько правил под конкретный движок (ниже).

**Итог коротко** (медианы `results/quick-3.json`, машина делилась с другими агентами — порядок величин надёжен,
мс ± 10–20 %):

| вариант | small | medium | large | дистрибутив |
|---|---|---|---|---|
| **`litehtml-sciter-litehtml`** (лучший) | **108 мс** | **120 мс** | **121 мс** | 1.79 MB (один exe) |
| `litehtml-sciter-litehtml-gpu` | 291 мс | 303 мс | 306 мс | 1.79 MB |
| `litehtml-sciter-sciter` | 426 мс | 426 мс | 428 мс | 18.75 MB (exe + sciter.dll) |

`baseline-win32` (пустое окно + GDI) на этой машине ≈ 70–90 мс, `cpp-d2d` (свой рендер) ≈ 70 мс. litehtml даёт почти
браузерную GitHub-вёрстку из того же CSS за ≈ +30–40 мс к полу; критический путь — software-растеризация первого
экрана (из неё ≈ 25 мс — цветные эмодзи). Sciter в ≈ 4 раза медленнее, в 10 раз тяжелее, CSS нестандартный, а главная
ручка (графический слой) в 6.0.5.0 ломает отрисовку — для FastMD не подходит.

Главный урок litehtml: **раскладка большого документа сверхлинейна и прожорлива по памяти** (3.7 MB одним документом
не укладывается в 30 с и занял бы гигабайты). Поэтому прототип держит документ как **стопку независимых
litehtml-документов по разделам** (разрез по заголовкам): первый экран — первый кусок ≈ 8 KB, остальные 228 кусков
large раскладываются 4 фоновыми потоками за ≈ 1.5–2.3 с после старта, далёкие от экрана куски выгружаются.

## Как собрать

```
pwsh -File bench/protos/litehtml-sciter/build.ps1
```

Скрипт: при отсутствии скачивает litehtml / md4c / заголовки Sciter / sciter.dll (curl), удаляет свои `obj/` и `out/`,
`cmake -G Ninja -DCMAKE_BUILD_TYPE=Release` + `cmake --build` через `bench/tools/msvc.cmd`. Чистая сборка ≈ 20 с.

```
out/litehtml/fastmd-litehtml.exe   1 878 016 байт (litehtml + gumbo + md4c + наш код, без своих DLL)
out/sciter/fastmd-sciter.exe          373 248 байт
out/sciter/sciter.dll              19 292 160 байт
```

Файлы: `CMakeLists.txt`; `src/common/mdpage.{h,cpp}` (чтение файла, md4c-html, разрез по заголовкам, argv),
`src/common/highlight.cpp` (подсветка синтаксиса);
`src/litehtml/main.cpp` (окно, потоки, модель кусков, прокрутка), `src/litehtml/container_d2d.{h,cpp}`
(document_container); `src/sciter/main.cpp`; `src/app.manifest` (PerMonitorV2). `style.css` превращается в
`obj/gen/style_css.h` на этапе configure.

## Варианты (`proto.json`)

| id | exe / аргументы | что это |
|---|---|---|
| **`litehtml-sciter-litehtml`** | `fastmd-litehtml.exe --rt=sw --no-ime` | лучший, конвейер ниже |
| `litehtml-sciter-litehtml-gpu` | `fastmd-litehtml.exe --rt=hwnd --no-ime` | та же раскладка, но классический `ID2D1HwndRenderTarget` (аппаратный D3D на RTX 5070), рисование в UI-потоке |
| `litehtml-sciter-sciter` | `fastmd-sciter.exe --no-ime` | Sciter.JS: `SciterCreateWindow` + `SCITER_APP_LOOP`, первые ≈ 4 KB markdown, остальное дописывается после первого кадра |

### Конвейер лучшего варианта

```
UI-поток:    fmb_init → argv → запуск worker → ImmDisableIME → CreateWindow → ShowWindow → цикл сообщений
worker:      чтение файла → md4c-html первого куска (markdown до первого заголовка после 8 KB) → DirectWrite →
             litehtml createFromString + render(ширина окна известна заранее: 1000 DIP − полоса прокрутки)
графпоток:   (параллельно раскладке) D2D factory + software DC render target + DIB-секция, прогрев цветных эмодзи
worker:      draw() первого экрана в DIB (Direct2D software/WARP)
WM_PAINT:    BitBlt DIB → EndPaint → DwmFlush → t_content          (PROTOCOL §3 для GDI/D2D)
после кадра: остальной markdown режется по заголовкам на куски ≈ 16 KB; 4 потока раскладывают их по порядку,
             UI вставляет каждый готовый кусок (высоты ещё не разложенных оцениваются по байтам, позиция чтения
             не прыгает); далёкие от экрана документы выгружаются (остаётся высота), при прокрутке — пересоздаются
```

Каждый кусок — отдельный litehtml-документ с тем же CSS плюс два правила «шва» (`padding-top:0` и сохранение
24 px у заголовка, который всегда начинает кусок; `padding-bottom:0` и нулевой нижний отступ последнего блока) —
вёрстка на стыке пиксель-в-пиксель совпадает с цельным документом (`shots/detail-litehtml-medium-chunk-seam-5100.png`).
Контейнер общий: шрифты дедуплицируются по описанию (со счётчиком ссылок), кэш «слово → `IDWriteTextLayout`» общий
и потокобезопасный (`shared_mutex`), фон корневого элемента не рисуется (иначе следующий кусок затирал бы предыдущий).

Честность: t_content — после `EndPaint` кадра с отрисованным документом и `DwmFlush()`. Первый экран — **настоящая
раскладка настоящего документа** (его первого куска, разрезанного по заголовку, поэтому первый экран идентичен
полному); если кусок ниже окна, он увеличивается ×4. Это разрешённая техника «first viewport first» (PROTOCOL §3).
Ни резидентных процессов, ни кэшей между запусками.

### Ручки (A/B-скрипт с чередованием конфигураций, medium, n = 5–6 в одной сессии)

| ручка | эффект |
|---|---|
| `--no-ime` (`ImmDisableIME(-1)` до создания окна) | `ShowWindow` ≈ 45–60 → ≈ 20 мс: **−30…40 мс** (TSF/IME инициализируется при первой активации окна). Вьюеру IME не нужен. Для Sciter — в пределах шума (там доминирует GPU) |
| D2D-цель создаётся в отдельном потоке параллельно раскладке (по умолчанию; `--serial-gfx` выключает) | ≈ −10 мс: software D2D = загрузка d3d11 + d3d10warp + WARP-устройство ≈ 15–30 мс |
| `--first=8192` против `--first=0` (весь файл одним документом до первого кадра) | medium 130 → 186 мс; large — **таймаут > 30 с**. `--first=4096` ≈ как 8192 |
| прогрев эмодзи (`--no-warm` выключает) | в пределах шума (≈ −5 мс): общий путь прогревается, но каждый новый глиф всё равно ≈ 4–5 мс |
| `--rt=hwnd` (аппаратный D2D) | **+200…250 мс**: создание D3D11-устройства NVIDIA внутри `CreateHwndRenderTarget` (как у `cpp-d2d-gpu`) |
| `--chunk=N`, `--pool=N` (размер фоновых кусков, число потоков) | на первый кадр не влияют; large: 4 потока — все куски за 1.5–2.3 с |
| Sciter `--no-dcomp` (`SCITER_ENABLE_DIRECT_COMPOSITION=FALSE`) | в пределах шума |
| Sciter `SCITER_SET_GFX_LAYER` (WARP, D2D, Skia, AUTO — любое значение) | **окно остаётся пустым**, хотя rAF×2 и `xcall` срабатывают. Ручка неработоспособна, используется слой по умолчанию (GPU) |
| Sciter `--first=0` (весь документ в `SciterLoadHtml`) | medium ≈ 0.8–1.4 с вместо ≈ 0.42 с (Sciter тратит ≈ 12–15 мс на KB markdown) |

### Sciter

Страница: `<html window-width="1000dip" window-height="800dip">` + `<meta charset=utf-8>` + style.css + статья. Скрипт
в конце `body`: `requestAnimationFrame(→ xcall('fastmd_frame') → requestAnimationFrame(→ xcall('fastmd_ready')))`;
хост ловит `HANDLE_SCRIPTING_METHOD_CALL` (обработчик окна через `SciterWindowAttachEventHandler`), делает `DwmFlush` и
пишет результат. t_window = первый rAF. В `SciterLoadHtml` уходят первые ≈ 4 KB markdown (до заголовка), остальное
дописывается после первого кадра кусками по 16 KB (`SciterSetElementHtml(article, SIH_APPEND_AFTER_LAST)`, по одному
на сообщение). sciter.dll грузится в отдельном потоке параллельно чтению и конвертации файла.

Отличия от `style.css` (для litehtml — `kExtraCss` в `src/litehtml/main.cpp`, для Sciter — `kExtraCss` в
`src/sciter/main.cpp`): `.task-list-item {list-style:none}` (md4c не ставит `ul.contains-task-list`); litehtml:
inline-код без `:not(pre) > code`, `table {display:table}` (нет «block-таблиц»), таблицы через
`border-collapse: separate; border-spacing: 0` с рамками справа/снизу у ячеек (в `collapse` litehtml неровно округляет
строки — линии 1 и 2 px вперемешку). md4c оставляет `\n` перед `</code></pre>`: браузер его съедает, litehtml и Sciter
рисуют лишнюю пустую строку — вырезается после конвертации.

## Куда уходит время

**litehtml (medium ≈ 110–125 мс):**

* ≈ 35–42 мс до `main` — создание процесса (CreateProcess + Defender + загрузчик). exe 1.9 MB со статическим CRT;
  d2d1/dwrite/imm32/WIC/ole32 — delay-load, при старте грузятся только user32/gdi32/kernel32/dwmapi.
* Раскладка первых 8 KB: md4c < 1 мс, gumbo + CSS + `render` ≈ 20–25 мс (≈ 380 `IDWriteTextLayout` на уникальные
  слова), параллельно созданию окна (CreateWindow ≈ 15 мс, ShowWindow ≈ 18 мс с `--no-ime`) и инициализации D2D.
* **Критический путь — растеризация первого экрана в software Direct2D: ≈ 25–35 мс**, из них ≈ 20–25 мс — цветные
  эмодзи (на первом экране medium их 6; тот же файл без эмодзи — ≈ 10 мс на весь экран). Segoe UI Emoji (COLR) в
  WARP-растеризаторе стоит ≈ 4–5 мс на каждый новый глиф.
* BitBlt + EndPaint + DwmFlush ≈ 8–15 мс.

**litehtml-gpu:** всё то же + ≈ 200 мс на `CreateHwndRenderTarget` (D3D11-устройство NVIDIA).

**Sciter (≈ 410–440 мс):** `SciterExec(SCITER_APP_INIT)` ≈ 35–50 мс; `SciterCreateWindow` ≈ 200–300 мс (движок сам
создаёт GPU-устройство; однажды было 12 мс — повторить не удалось); `SciterLoadHtml` 4 KB ≈ 70–100 мс (парсинг ≈ 8 мс,
остальное — стили и раскладка; весь medium — 0.7–1.1 с, дороже всего таблицы ≈ 14 мс на таблицу из 6 строк); показ и
два кадра до rAF ≈ 35–55 мс. Рабочее множество ≈ 60 MB, commit ≈ 137 MB, 18.7 MB на диске.

## Идеи дальнейшего ускорения (litehtml)

1. **Эмодзи вне критического пути**: сразу после чтения файла (эмодзи в первом куске известны до раскладки)
   растеризовать их на 2–4 потоках в маленькие битмапы и рисовать `DrawBitmap` — ≈ −20 мс на medium.
2. **Растеризация без WARP**: `IDWriteBitmapRenderTarget` (GDI DIB) + `TranslateColorGlyphRun`/`DrawPaintGlyphRun`
   для эмодзи и AA-примитивы вручную, как в `cpp-d2d` (там это дало ≈ −70 мс против WARP) — ≈ −15…25 мс.
3. Разбить первый экран на 2–3 полосы и растеризовать параллельно (контекст рисования передавать через `hdc`
   litehtml / thread_local, клипы у litehtml идут без `hdc`).
4. Меньший exe: ≈ 0.6 MB — таблицы кодировок litehtml (`encodings.cpp`), не нужные для UTF-8.
5. Фоновые куски: предвыборка соседей при прокрутке (сейчас выгруженный кусок пересоздаётся синхронно, ≈ 20–40 мс
   на 16 KB — заметная «ступенька» при быстром перетаскивании ползунка по large), хранить не `IDWriteTextLayout`,
   а глиф-раны (память кэша слов).
6. Кэш «последнего кадра» / резидентный процесс — другая категория (`-resident`, см. `cpp-d2d-resident`).

## Оценка трудозатрат на продукт на litehtml

Прототип (≈ 1 750 строк нашего кода) закрывает показ, прокрутку, большие файлы и простую подсветку кода. Для продукта:

| задача | оценка |
|---|---|
| Доводка кусочной модели: предвыборка, перераскладка при resize в фоне, якоря/переходы по ссылкам между кусками | 1–1.5 недели |
| Выделение текста и копирование (hit-test по `render_item`, свои структуры поверх litehtml, выделение через куски) | 1.5–2 недели |
| Поиск по документу с подсветкой (по markdown/тексту кусков, прокрутка к совпадению) | 1 неделя |
| Подсветка синтаксиса уровня GitHub (сейчас простой лексер; tree-sitter/грамматики → `<span class>`), KaTeX/Mermaid — только фоновый рендер в SVG/PNG | 1–2 недели (без математики/диаграмм) |
| Ссылки, оглавление, drag&drop, ассоциация `.md`, автообновление при изменении файла | 1 неделя |
| Тёмная тема, настройки, HiDPI/многомониторность, печать | 1 неделя |
| Правки/патчи litehtml (padding inline, border-collapse, скорость) и сопровождение форка | 1–2 недели + поддержка |
| **Итого** | **≈ 2–2.5 месяца** одного разработчика до качественного вьюера |

Sciter для продукта не рекомендую: 0.4–0.6 с на старт, 19 MB, закрытый движок (исходники платно, атрибуция
в About), нестандартный CSS, неработающая ручка графического слоя.

## Подводные камни

* **litehtml раскладывает большие документы сверхлинейно и дорого по памяти.** Один `render()` на весь документ:
  100 KB — 0.16 с, 200 KB — 0.36 с, 400 KB — 0.69 с, 800 KB — 1.8 с, 1.6 MB — 5.6 с, 3.7 MB — не уложился в 30 с;
  память ≈ 700 байт на байт markdown (DOM + вычисленные стили + render-дерево). `draw()` обходит всё дерево даже с
  `clip` (на 1.6 MB — ≈ 0.4 с на кадр). Отсюда кусочная модель с выгрузкой; куски режутся только по заголовкам
  верхнего уровня (`fmd::heading_cut`, вне fenced-кода): документ без заголовков остаётся одним куском.
* Разрез md по заголовкам ломает только ссылки-определения (`[x]: url`), объявленные в другом куске.
* Базовая линия: `SetLineSpacing(UNIFORM, ascent+descent, ascent)` на каждом формате, иначе fallback-шрифты
  (эмодзи, CJK) сдвигают строку. Позиции litehtml дробные — рамки и заливки прилипают к пикселям, иначе 1-px линии
  расплываются на два ряда.
* litehtml зовёт `text_width` на каждое слово: нужен кэш «слово → `IDWriteTextLayout`» с гетерогенным поиском
  (`std::string_view`, без аллокаций); при нескольких документах — общий и потокобезопасный.
* Фон корневого элемента в litehtml закрашивает весь холст — в стопке документов его рисовать нельзя.
* litehtml не рисует `<input>` → task-list-чекбоксы подменяются разметкой.
* `ImmDisableIME` даёт −30…40 мс любому Win32-окну на этой машине (инициализация TSF при первой активации).
* Sciter 6.0.5.0: окно, созданное хостом и управляемое через `SciterProcND`, остаётся пустым — работает только
  `SciterCreateWindow` + `SCITER_APP_LOOP`; любой `SCITER_SET_GFX_LAYER` → пустое окно, но rAF×2 и `xcall`
  срабатывают — сигнал «кадр готов» от страницы не доказывает, что что-то нарисовано (проверять глазами/экраном).
  Без `<meta charset>` Sciter читает страницу как cp1251; без `window-width/height` ставит 800×600 и раскладывает
  документ дважды.
* Скриншоты: другие агенты открывают окна поверх — захват экрана ненадёжен; `PrintWindow` (harness) у этих окон
  работает. Первый запуск только что собранного exe — до 10 с (Defender).

## Аудит (независимая проверка, 2026-09-19)

**Вердикт: сравнение честное, все три варианта годны для финального последовательного замера.** Одна правка
«гигиены» (прогрев эмодзи, ниже), на цифры она не влияет.

### Что проверено

| пункт | результат |
|---|---|
| t_content по PROTOCOL §3 (GDI/D2D) | `litehtml`: первый экран рисуется worker'ом в DIB (software D2D), в `WM_PAINT` — `BitBlt` → `EndPaint` → `fmb_content_presented_ex` (внутри `DwmFlush()`, потом метка). `-gpu`: `ID2D1HwndRenderTarget::EndDraw` (= Present) → `DwmFlush` → метка. Метка ставится только когда `g_chunks` не пуст, т.е. в кадре настоящий разложенный документ, а не фон |
| t_content по §3 (веб-движки) | Sciter: rAF → rAF → `Window.this.xcall('fastmd_ready')` → хост `DwmFlush` → метка — ровно процедура протокола |
| «first viewport first» | законно: первый кусок — настоящий markdown до заголовка после 8 KB (Sciter — 4 KB), разложенный litehtml целиком; если он ниже окна — увеличивается ×4. Первый экран пиксель-в-пиксель совпадает со снимком после фоновой раскладки |

| сборка | `CMAKE_BUILD_TYPE=Release`, `/O2 /Ob2 /GL /Oi /Gy /GS- /MT`, линковка `/LTCG /INCREMENTAL:NO`, delay-load d2d1/dwrite/WIC/ole32/imm32 (проверено по `obj/build.ninja`); `build.ps1` пересобирает с нуля за ≈ 20 с — пересобрал, всё собралось |
| `bench.py check` medium + large, все варианты | CHECK OK, предупреждений нет; `observed_ms` ≤ `window_ms` ≤ `content_ms` везде (litehtml: obs 57–63, win 66–70, content 107–110 мс) |

**Независимая проверка пикселей** (свой скрипт вне репозитория: опрос содержимого окна через
`PrintWindow(PW_CLIENTONLY | PW_RENDERFULLCONTENT)` с отметкой времени, сравнение с установившимся кадром):
у `litehtml` последний пустой кадр приходится на t_content − 9…33 мс, первый кадр с документом — на
t_content + 15…46 мс (один захват длится 20–50 мс), т.е. t_content лежит внутри окна перехода — **метка не ранняя**.
`-gpu` — то же (документ виден через 10–20 мс после t_content). Для Sciter `PrintWindow` блокируется, пока UI-поток
грузит страницу (≈ 170 мс), и сам сдвигает замер — точно подтвердить пиксели не удалось, но и противоречий нет
(в двух прогонах документ уже был в окне раньше метки). Снимок экрана через DC рабочего стола для этой цели
непригоден: анимация открытия окна Windows (≈ 150–250 мс «проявления») и окна других агентов поверх.

### Исправлено

* **Прогрев цветных эмодзи рисовал ровно тот глиф, что стоит на первом экране корпуса.** `gfx_worker` рисовал
  U+1F680 🚀 в тот же software-render target, которым потом рисуется документ; 🚀 — самый частый эмодзи корпуса
  (small ×1, medium ×41, large ×2890) и есть на первом экране всех трёх файлов, т.е. его растеризация заранее попадала
  в кэш глифов. Это зависимость от корпуса, «зашитая» в код. Заменил на U+1F600 😀 — его в корпусе нет (в корпусе
  только U+1F680, U+2728, U+1F4C4, U+2705, U+274C, U+26A1). Общий прогрев COLR-пути остаётся.
  Эффект, A/B с чередованием, n = 10, медианы t_content: старый exe (🚀) medium 119.2 / small 104.2 мс,
  новый (😀) 114.2 / 102.4 мс, новый с `--no-warm` 113.9 / 96.6 мс — всё в пределах шума, **выигрыша от «угаданного»
  глифа не было**, правка — гигиена. Файл: `src/litehtml/main.cpp` (`gfx_worker`). Пересобрано `build.ps1`.

### Для финального сравнения стоит знать

* `--no-ime` (`ImmDisableIME(-1)`) — законный приём, но это выбор приложения, а не стека: A/B n = 8 (medium) —
  `ShowWindow` 18.6 против 39.6 мс, t_window 65 против 92 мс, а **t_content всего −8.6 мс** (105.7 против 114.3),
  потому что критический путь — растеризация на worker'е. Продукту с полем поиска и CJK-вводом IME придётся вернуть
  (или создать окно поиска в другом потоке).
* `-gpu`: если документ готов до первого `WM_PAINT`, t_window ≈ t_content (окно видно с ≈ 60 мс, но до создания
  аппаратного target'а ≈ 200 мс в нём ничего не нарисовано). По определению t_window это честно; для пользователя —
  ≈ 200 мс непрорисованного окна.
* `litehtml` large = medium по времени (≈ 110 мс): до первого кадра обрабатывается только первый кусок ≈ 8.7 KB,
  3.7 MB лишь читаются с диска (≈ 3 мс). Это разрешённая техника; вся раскладка large завершается в фоне за 1.5–2.3 с,
  большой документ прокручивается (снимок `shots/audit-litehtml-sciter-litehtml-large.png`).
* Sciter: известные огрехи вёрстки (таблица на всю ширину колонки со срезанной правой рамкой, inline-код без
  padding/скругления, серые нативные чекбоксы, синтетический курсив) подтверждаю по снимкам.
