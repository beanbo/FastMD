# cpp-webview2 — C++ Win32 + WebView2 + md4c-html

Прототип FastMD на стеке «тонкий нативный хост + системный Chromium (WebView2)». Markdown парсится в C
(md4c → HTML), страница со встроенным `bench/common/style.css` отдаётся в WebView2, момент `t_content`
фиксируется строго по PROTOCOL §3: контент в DOM → `requestAnimationFrame` ×2 → `postMessage('painted')` →
в хосте `DwmFlush()` → `t_content`.

**Итог в одну строку:** холодный старт ≈ **0.5–0.6 с** до отрисованного документа на этой машине
(белое окно появляется через ~0.07–0.1 с), и почти всё это время — запуск процессов WebView2 Runtime, а не
наш код. Резидентный вариант — **~70–110 мс**. Ниже 0.45 с холодный WebView2 здесь не опускается ни с какими
флагами, которые можно честно выпускать.

## 1. Стек и версии

| Компонент | Версия / детали |

| Markdown | md4c **0.5.3** (`release-0.5.3`), md4c-html, диалект `MD_DIALECT_GITHUB`; исходники не изменены (`third_party/md4c`) |

Файлы:

- `src/app.cpp` — хост: окно, WebView2 environment/controller, навигация, протокол бенча, резидентный режим;
- `src/mdconv.c/.h` — обёртка над md4c-html: точки разреза по границам блоков верхнего уровня (для «сначала первый экран»), подсветка fenced-кода, чтение файла;
- `src/launcher.c`, `src/ipc.h` — `fastmd-open.exe` и контракт `WM_COPYDATA` для `-resident`;
- `src/app.manifest` — PerMonitorV2 DPI, UTF-8 code page;
- `build.ps1`, `proto.json`; `results/*.json` — сырые прогоны из этого README; `shots/*.png` — скриншоты.

## 2. Сборка

```
pwsh -File bench/protos/cpp-webview2/build.ps1
```

Неинтерактивно, ~10 с. Если нет `third_party/`, скрипт сам скачивает NuGet-пакет WebView2 (nuget.org) и 6
файлов md4c (raw.githubusercontent.com, тег `release-0.5.3`) — оба URL проверены. Затем пересоздаёт `out/`
и `obj/`, генерирует `obj/gen/style_css.h` из `bench/common/style.css` (CSS вшивается в exe, комментарии
вырезаются) и компилирует через `bench/tools/msvc.cmd`.

Профиль WebView2 (user data folder) — `%LOCALAPPDATA%\FastMD\WebView2-<variant id>`: не рядом с exe
(WebView2 по умолчанию пишет `<exe>.WebView2\` в папку программы — это и мусор в `out/`, и невозможно
в Program Files). Папки `WebView2-cpp-webview2-x-*` там — остатки экспериментов, их можно удалить руками.

## 3. Как устроен холодный старт (вариант `cpp-webview2`)

1. `wWinMain`: `fmb_init` (mark `main`) → `CoInitializeEx` (STA) → **сразу** `CreateCoreWebView2EnvironmentWithOptions`.
   На runtime 153 completion-колбэк приходит синхронно внутри вызова, и в нём же вызывается
   `CreateCoreWebView2ControllerWithOptions` — именно он запускает `msedgewebview2.exe`. Контроллер создаётся на
   message-only «парковочном» окне (`--early=1`), настоящее окно ещё не существует.
2. Параллельно рабочий поток читает файл и конвертирует его md4c → HTML (medium: <1 мс, large 3.7 МБ: ~20–35 мс),
   запоминая смещения границ блоков верхнего уровня.
3. Создаётся и **сразу показывается** белое окно 1000×800 DIP (`t_window` ≈ 70–100 мс от CreateProcess).
4. `ctrl_ready`: контроллер переносится в настоящее окно (`put_ParentWindow` + переключение `IsVisible`, иначе
   rAF никогда не срабатывает — см. «Грабли»), настраиваются settings, и выполняется `NavigateToString` страницы, в
   которой только **первые ~24 КБ HTML** (целые блоки верхнего уровня; это заведомо больше первого экрана).
5. Страница: CSP с nonce, `<base href="https://dXXXXXXXX.doc.fastmd.example/">` + `SetVirtualHostNameToFolderMapping`
   на папку документа (локальные картинки), `style.css` inline. После `DOMContentLoaded` → rAF → rAF →
   `chrome.webview.postMessage('painted')` → в хосте `DwmFlush()` → `t_content`.
6. После первого кадра остаток документа дописывается сообщениями `PostWebMessageAsString('A'+html)` кусками по
   256 КБ (`insertAdjacentHTML`). **Это легальная техника «сначала первый экран» (PROTOCOL §3)**: первый экран —
   настоящий отрендеренный документ, остальное догружается за следующие ~100–300 мс (large: 28 кусков).
7. Ссылки из документа открываются в браузере по умолчанию (`NavigationStarting`/`NewWindowRequested` отменяются).

Если первая страница больше 1.5 МБ (например `--chunk=0` на large.md), `NavigateToString` не годится (лимит 2 МБ,
`E_INVALIDARG`) — хост автоматически переключается на `Navigate("https://page.fastmd.example/doc.html")` +
`WebResourceRequested`, который отдаёт страницу из памяти.

## 4. Варианты (`proto.json`)

| id | exe / args | Что это |
|---|---|---|
| **`cpp-webview2`** (лучший честный) | `out/fastmd-wv2.exe --variant=cpp-webview2` | Всё из §3 + браузерные аргументы по умолчанию (см. ниже), EnvironmentOptions: `ExclusiveUserDataFolderAccess=FALSE`, `EnableTrackingPrevention=FALSE`, `AreBrowserExtensionsEnabled=FALSE`; ControllerOptions: белый `DefaultBackgroundColor`; settings: без DevTools/статус-бара/автозаполнения/swipe/SmartScreen-проверки |
| `cpp-webview2-default` | `--untuned --chunk=0` | Эталон «как в примере Microsoft»: без options-объектов, без browser args, GPU-процесс включён, весь документ одной страницей (large → через `WebResourceRequested`). Профиль тоже в `%LOCALAPPDATA%` |
| `cpp-webview2-resident` | `out/fastmd-open.exe` + resident `fastmd-wv2.exe --resident` | **Резидентный** (PROTOCOL §6), см. §4.2 |

Браузерные аргументы варианта `cpp-webview2` (`kBaseArgs + kLeanArgs` в `app.cpp`; `--gpu=1` отключает вторую часть):

```
--disable-features=msSmartScreenProtection,msWebOOUI,msPdfOOUI,msEdgeTranslate
--disable-background-networking --disable-component-update --no-first-run --disable-default-apps
--disable-sync --disable-extensions
--disable-gpu --in-process-gpu --enable-features=NetworkServiceInProcess2,NetworkServiceInProcess
```

Это конфигурация по умолчанию для обычного запуска `fastmd-wv2.exe file.md` (т.е. то, что будет при двойном клике).

### 4.1 Проверенные ручки (knobs) и почему выбрано именно это

Все ручки остались в `app.cpp` как аргументы командной строки. Замеры на medium.md, `t_content`, медиана,
чередующийся порядок; машину параллельно грузили другие агенты (CPU 45–70 %), поэтому смотреть надо на
разницу по фазам, а не на абсолютные значения. Сырые данные — `results/knobs-medium-*.json`.

| Конфигурация | Медиана, мс | Процессов | CPU на запуск, мс | Главное по фазам |
|---|---|---|---|---|
| `--single-process` (+ base args) | 547 / 563 | 3 | 1100 | рендерер в процессе браузера: nav→DCL 34 мс вместо ~165, но env→ctrl +30 мс, первый кадр +55 мс |
| **lean: `--disable-gpu --in-process-gpu` + NetworkServiceInProcess (выбрано)** | **566 / 584 / 535** | **5** | **1130** | DCL→кадр 3–4 мс |
| `--disable-gpu` | 579 / 579 | 7 | 1430 | DCL→кадр 4 мс |
| `--nav=script` (ExecuteScript + `document.write` в исходный about:blank, без навигации) | 600 | 7 | 1500 | выигрыша нет: рендерер всё равно стартует только на первом скрипте/навигации |
| `--no-sandbox` | 630 | 7 | 1590 | выигрыша нет |
| tuned с GPU-процессом (`--gpu=1`) | 612 / 632 / 620 | 7 | 1520–1610 | DCL→кадр 19–32 мс (ждём GPU-процесс) |
| `--in-process-gpu` без `--disable-gpu` | 666 | 6 | 1625 | на уровне default, выигрыша нет |
| default (untuned) | 665 / 644 | 7 | 1750–1800 | DCL→кадр 17–46 мс |

Дополнительно (`results/knobs-medium-3.json`, `-4.json`, lean как база):

| Ручка | Эффект |
|---|---|
| `--early=0` (контроллер сразу на настоящем скрытом окне, без парковки) | 535 vs 535 — одинаково; оставлен `--early=1` |
| `--envlast` (сначала показать окно, потом стартовать WebView2) | **+37 мс** — создание/показ окна до старта env попадает на критический путь |
| `--udf=fresh` (новый профиль каждый раз) | env→ctrl +40 мс (создание профиля) |
| `--inprivate` | в шуме |
| `--nav=resource` (`WebResourceRequested` вместо `NavigateToString`) | в шуме (+5–10 мс) |
| `--chunk=0` (весь medium одной страницей) | +20–30 мс на medium (DCL 126 vs 102), на large — **2.7 с против 0.54 с** |

Почему не `--single-process`: флаг Chromium «только для отладки», в WebView2 официально не поддерживается,
отключает sandbox и изоляцию рендерера, известен падениями; выигрыш ~20 мс (в шуме). Для продукта неприемлем —
в финальных вариантах его нет. `--no-sandbox` не даёт ничего и ухудшает безопасность.

Цена выбранного lean-режима: композиция и растеризация программные (Skia на CPU). Для текстового просмотрщика
картинка та же (скриншоты medium lean и резидентного GPU-варианта различаются в 77 пикселях из 794 тыс.), но прокрутка
большого документа на 4K ест больше CPU. `--in-process-gpu` и сетевой сервис в процессе браузера официально в
WebView2 не документированы — работают на runtime 153 (десятки запусков без сбоев), но это риск при обновлении
runtime. Консервативная альтернатива — только `--disable-gpu` (разница ~10 мс, но 7 процессов и +25 % CPU).

### 4.2 Резидентный вариант (`cpp-webview2-resident`) и соответствие PROTOCOL §6

- `proto.json` → `"resident": {"exe": "out/fastmd-wv2.exe", "args": ["--resident", ...]}`; харнесс запускает его
  один раз вне замера. Резидент создаёт message-only окно `FastMDWebView2Resident`, environment, **скрытый**
  контроллер и загружает «пустую» страницу-оболочку (CSS + скрипт). GPU-процесс в резиденте включён (`--gpu=1`
  по умолчанию для `--resident`) — время его старта не замеряется, а прокрутка лучше.
- Замеряется `fastmd-open.exe` (103 КБ, только kernel32/user32/shell32): берёт абсолютный путь, `FASTMD_BENCH_OUT`
  и `FASTMD_BENCH_EXIT`, отправляет `WM_COPYDATA` резиденту (`AllowSetForegroundWindow` для активации) и выходит.
  Если резидента нет — обычный холодный запуск `fastmd-wv2.exe`.
- Резидент: конвертирует файл, `PostWebMessageAsString('D'+base+html первого экрана)`, показывает окно
  (`"<file> — FastMD (cpp-webview2-resident)"`), страница → rAF ×2 → `painted` → `DwmFlush` → **резидент** пишет
  файл результата (mark `launcher_main` — время старта лаунчера). Затем при `FASTMD_BENCH_EXIT != 0` окно документа
  закрывается для пользователя (скрывается, контроллер `IsVisible=FALSE`, DOM очищается), процесс продолжает жить.
  Закрытие окна крестиком в обычном режиме делает то же самое.
- Id оканчивается на `-resident` — это единственный вариант с предзапущенным процессом.

## 5. Поддержка спецификации (PROTOCOL §5)

Скриншоты (`bench.py shot`, 1000×800 DIP): `shots/cpp-webview2-medium.png`, `shots/cpp-webview2-small.png`,
`shots/cpp-webview2-resident-medium.png`, и глубже по medium — `shots/cpp-webview2-medium-scroll780.png`,
`shots/cpp-webview2-medium-scroll1560.png`, а также `shots/cpp-webview2-large-scroll300000.png` — раздел 208 из
large.md, т.е. контент, дописанный кусками уже после первого кадра (сделаны с `FASTMD_WV2_SCROLL=<px>`, dev-переменная).

Поддерживается (проверено глазами на скриншотах):

- заголовки h1–h6 с размерами из спецификации, линия под h1/h2, h6 серым; абзацы с переносом по словам;
- **жирный** / *курсив* / `inline code` / ~~зачёркнутый~~ / ссылки `#0969da` (открываются в браузере по умолчанию);
- маркированные, нумерованные, вложенные списки, **task lists** (чекбоксы disabled, как на GitHub; md4c не ставит
  класс `contains-task-list`, поэтому в `kExtraCss` добавлено `.task-list-item{list-style-type:none}`);
- цитаты (полоса 4 px), горизонтальные линии, таблицы GFM с выравниванием колонок и зеброй;
- fenced-код: `Cascadia Mono`, фон `#f6f8fa`, радиус 6, **без переноса строк, с горизонтальной прокруткой**;
  **подсветка синтаксиса** (встроенная, в C, при конвертации): C/C++, Rust, C#/Java/Kotlin, JS/TS, Python,
  PowerShell, JSON, Bash, Go — ключевые слова, строки, комментарии, числа, функции, типы; цвета как у GitHub light;
- **локальные картинки** (PNG из `img/` рядом с документом) через `SetVirtualHostNameToFolderMapping`;
- Unicode: кириллица, CJK, цветные эмодзи (Segoe UI Emoji через DirectWrite fallback Chromium);
- PerMonitorV2 DPI (манифест + `WM_DPICHANGED`), клиентская область 1000×800 DIP, светлая тема, прокрутка,
  Ctrl+колесо — масштаб (штатно в WebView2), выделение и копирование текста.

Не поддерживается / упрощено:

- сноски, front matter, формулы (KaTeX/MathJax), Mermaid — md4c их не умеет, JS-библиотеки намеренно не грузим;
- якоря у заголовков (md4c не генерирует `id`), оглавление;
- поиск по странице (своего UI нет, штатный Ctrl+F WebView2 не проверял; в SDK есть Find API — дело пары дней), печать, тёмная тема, автообновление при
  изменении файла, drag&drop, открытие относительных ссылок на другие `.md` внутри просмотрщика;
- подсветка — эвристическая (не полноценный лексер), без многострочных raw-строк Rust/C#.

### Разбивка по маркам (медианы, мс от CreateProcess; lean, medium)

| Фаза | мс | Что происходит |
|---|---|---|
| CreateProcess → `main` | 20–40 | загрузка exe (443 КБ, статический CRT), Defender |
| `main` → `env_call` | 14 | почти всё — `CoInitializeEx` (13 мс, combase/RPC); без STA COM WebView2 не работает |
| `env_call` → `ctrl_ready` | **300–390** | **запуск WebView2 Runtime**: `msedgewebview2.exe` + `msedge.dll` (332 МБ), профиль, crashpad, (GPU/network — в lean внутри браузера), создание WebContents. Наш процесс в это время создаёт и показывает окно и конвертирует документ |
| `ctrl_ready` → `nav` | 3–6 | settings, обработчики, `NavigateToString` |
| `nav` → `content_loading` | 62–75 | запуск процесса рендерера + коммит навигации |
| `content_loading` → `DOMContentLoaded` | 70–100 | инициализация Blink/V8 в новом рендерере, разбор HTML/CSS первой страницы |
| `DOMContentLoaded` → `painted` (rAF×2) | **3–4** (с GPU-процессом 17–46) | первый кадр |
| `painted` → `t_content` | 6–9 | `DwmFlush` |

Резидент (medium): CreateProcess лаунчера → его `main` ~40 мс (Defender), `WM_COPYDATA` <1 мс, конвертация+post
1 мс (large: 35 мс — md4c парсит весь 3.7 МБ файл до отправки первого экрана), post → `painted` 21–32 мс, `DwmFlush` 8 мс.
Это установившийся режим; **первый** документ после старта резидента (`bench.py check`, прогон #0 в `run`)
занимает 165–280 мс — рендерер ещё холодный (JIT, кэши шрифтов/стилей), в `run` он отбрасывается как разогрев.

## 7. Куда уходит время (вывод)

~85 % холодного старта — это WebView2 Runtime: ~60 % на старт browser-процесса и ~30 % на старт рендерера. Всё,
что делает наш код (чтение, md4c, подсветка, окно), либо <20 мс, либо спрятано параллельно за стартом браузера.
Никакие флаги не уменьшают старт browser-процесса заметно (он в пределах шума у всех вариантов); флаги
реально влияют только на хвост: GPU-процесс (−15…−40 мс на первом кадре) и число процессов/CPU.
Практический пол этого стека холодным стартом на этой машине — **~0.45–0.5 с**; «как пуля» (≤100 мс)
достижимо только резидентом или при уже открытом окне (~0.33 с).

## 8. Идеи дальнейшего ускорения

1. **Резидент как опция продукта** (трей/автозапуск; ~20–30 МБ WS хоста + ~150–180 МБ commit процессов WebView2
   постоянно в памяти) — 70–110 мс.
2. **Переиспользовать уже открытое окно/процесс** (single-instance: второй двойной клик отдаёт путь первому
   процессу через `WM_COPYDATA` и открывает новую вкладку/окно в том же WebView2 environment) — без резидента,
   но второй и последующие файлы открываются за ~70–100 мс (как резидент), а не 330 мс.
3. Для large в резиденте: парсить md4c только префикс файла (до безопасной границы вне fenced-блока) для первого
   экрана, остальное — на рабочем потоке (−30 мс на 3.7 МБ; риск — reference-ссылки, определённые ниже по тексту).
4. Резидент: после старта «прогреть» рендерер скрытым образцом документа (заголовки, код, таблица, эмодзи — шрифты,
   стили, JIT), чтобы и **первый** документ открывался за ~80 мс, а не за 165–280 мс.
5. `CoInitializeEx` (13 мс) — единственный заметный кусок нашего кода на критическом пути; проверить
   `COINIT_DISABLE_OLE1DDE` и отложенную загрузку лишних DLL (`/DELAYLOAD:shell32.dll` и т.п.) — ~5–10 мс.
6. Fixed-version runtime рядом с приложением ничего не ускорит (тот же `msedge.dll`), но даст контроль над
   `--in-process-gpu`-рисками; стоит +~250 МБ дистрибутива.
7. Исключение папки runtime из сканирования Defender (админ) — в продукте невозможно, но объясняет часть разброса.

## 9. Оценка трудозатрат на полноценный продукт на этом стеке

| Этап | Оценка (1 разработчик C++) |

Сильные стороны стека: качество типографики и Unicode «бесплатно» (Chromium + DirectWrite), CSS-стилизация

## 10. Грабли

- **`NavigateToString` > 2 МБ** → `E_INVALIDARG`, окно навсегда белое. Решение: первая страница маленькая (первый
  экран), либо `Navigate(https://...)` + `WebResourceRequested` (сделано автоматически при >1.5 МБ).
- **Имя виртуального хоста**: `.local` или имя без точки добавляет ~1.9 с на каждую навигацию (разрешение имени).
  Используем `*.fastmd.example` (подходит `.example`/`.invalid`/`.localhost`).
- **Контроллер, созданный под невидимым (message-only) родителем**, после `put_ParentWindow` не рисует и rAF не
  срабатывает, пока не переключить `put_IsVisible(FALSE)` → `put_IsVisible(TRUE)` + `NotifyParentWindowPositionChanged`.
- На runtime 153 completion-колбэк `CreateCoreWebView2EnvironmentWithOptions` вызывается синхронно; browser-процесс
  стартует в `CreateCoreWebView2Controller` — поэтому контроллер нужно создавать как можно раньше (парковочное окно
  или скрытое настоящее окно — одинаково; а вот показать окно до старта env стоит +37 мс).
- **User data folder по умолчанию** — `<exe>.WebView2` рядом с exe: не работает в Program Files и раздувает dist.
- Экземпляры с одним UDF, но **разными browser args/options**, не могут делить browser-процесс (по документации
  WebView2 создание environment в этом случае падает; сам я это не проверял) — поэтому у каждого варианта свой UDF.
- Runtime 153 **оставляет процесс crashpad-handler на каждого клиента**, подключающегося к общему
  browser-процессу (наблюдение исследователя веб-движков; в замере «второго окна» в job клиента 3 процесса).
  Для single-instance продукта это ещё один аргумент открывать новые документы в уже живом процессе.
- `--single-process` «работает», но не поддерживается и небезопасен; `--no-sandbox` бесполезен.
- `ExecuteScript` в исходный `about:blank` не экономит старт рендерера (он создаётся лениво).
- md4c-html не выдаёт `class="contains-task-list"`/якоря заголовков; нет сносок.
- Под Defender каждый новый процесс стоит 20–40 мс, а WebView2 стартует 5–7 процессов — это главный источник
  разброса замеров; изредка запуск exe стопорится на секунды (виден выброс 2.1 с до `main`).

## 11. Отладочные переменные

- `FASTMD_WV2_LOG=<file>` — трассировка HRESULT/событий WebView2 (по умолчанию выключена, ноль затрат).
- `FASTMD_WV2_SCROLL=<px>` — после первого кадра прокрутить документ (для скриншотов глубже первого экрана через `bench.py shot`).
- Ручки командной строки перечислены в шапке `src/app.cpp` (`--gpu`, `--nav`, `--chunk`, `--slice`, `--hl`, `--cv`,
  `--udf`, `--early`, `--envlast`, `--inprivate`, `--fluent`, `--tp`, `--bargs`, `--untuned`).

### Независимая проверка `t_content` по пикселям экрана (`tools/pixcheck.py`)

Скрипт запускает exe как харнесс (Job Object, те же переменные окружения) и в цикле снимает с экрана (BitBlt
экранного DC, то есть то, что скомпоновал DWM) полосу 900×200 клиентской области: ~6–12 мс на снимок. В таблице
«последний снимок без текста» — это начало такого снимка, «первый с текстом» — его конец; всё в мс относительно
`t_content`. Учитывались только прогоны без перекрытия чужими окнами.

| Вариант | Чистых прогонов | Последний снимок без текста | Первый снимок с текстом | Вывод |
|---|---|---|---|---|
| `cpp-webview2` (lean, без GPU-процесса) | 10 | −24…+1.4 | +1…+20 | марка **точная** (в пределах одного снимка/кадра) |
| `cpp-webview2-default` (GPU-процесс) | 5 | +10…+18 | +32…+45 | текст на экране на **~15–35 мс позже** `t_content` |
| `cpp-webview2 --gpu=1` (tuned + GPU-процесс) | 3 | +1…+19 | +20…+32 | то же, ~10–30 мс |
| `cpp-webview2-resident`, устойчивый режим (окно не скрывается, документы small/medium чередуются, `--keep`) | 7 | −24…−11 | −5…+1.8 | марка **точная** |

Вывод по GPU-процессу: при холодном старте с отдельным GPU-процессом rAF×2 + `DwmFlush` срабатывают раньше, чем
GPU-процесс отдаёт свой первый кадр в DWM. Прототип при этом следует процедуре PROTOCOL §3, поэтому я его не
менял: другие веб-прототипы используют ту же процедуру, и правка только здесь сделала бы сравнение нечестным.
Для оркестратора: у всех веб-стеков с GPU-процессом (Electron-gpu, wry/Tauri, winui3-webview2 и т.п.) `t_content`,
вероятно, так же оптимистичен на 10–35 мс. У lean-варианта (программная композиция) и у резидента в устойчивом
режиме этого эффекта нет.

### Найденные визуальные дефекты (на честность замера не влияют)

1. **Тёмная вспышка в lean-режиме (`cpp-webview2`).** Между `ctrl_ready` и первым кадром (≈440–590 мс от старта)
   область WebView2 55–80 мс залита цветом `#131313`. Это видно во всех чистых прогонах; снимок полосы —
   `shots/audit-dark-flash-band.png`. Пользователь видит последовательность «белое окно → тёмный прямоугольник →
   документ». Причина — `--disable-gpu` (программная композиция): с `--gpu=1` и в `default` вспышки нет или она ≤10 мс,
   а `--early=0` не помогает. На `t_content` вспышка не влияет, потому что марка ставится после неё. Для продукта это
   нужно чинить: например, белым дочерним окном-заглушкой поверх WebView2 до `painted` или отказом от
   `--disable-gpu` (≈ +20–40 мс по марке и ещё +10–30 мс до реальных пикселей).
2. **Резидент показывает прошлый документ.** При повторном показе окна DWM на мгновение выводит последний кадр
   предыдущего документа: очистка DOM (`'C'`) выполняется уже скрытым контроллером и не отрисовывается. В трассе с
   чередованием small/medium до нового документа видна пиксельная подпись старого. На марку это не влияет, потому
   что `t_content` ставится после кадра нового документа. Для продукта: чистить или прятать контент до скрытия окна
   либо показывать окно только после `painted`.
3. **Второй резидент молча выходит.** `--resident` при уже живом резиденте завершается сам (`FindWindowExW` по
   глобальному классу `FastMDWebView2Resident`), и лаунчер отдаёт документ чужому резиденту. Во время аудита
   параллельный `bench.py run all` другого агента держал свой экземпляр, и мои запросы уходили в него. В финальном
   последовательном замере это не мешает, но гонять `-resident`-варианты двумя харнессами одновременно нельзя.
