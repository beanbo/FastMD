# cpp-richedit — Win32 + встроенный RichEdit 8 (msftedit.dll) + md4c → RTF

Путь «ноль зависимостей, только то, что уже есть в Windows»: markdown разбирается md4c, превращается в RTF и
заливается в системный контрол RichEdit (`msftedit.dll`, класс `RICHEDIT50W`) через `EM_STREAMIN`.
Два способа хостинга RichEdit: классическое дочернее окно и **windowless** (`CreateTextServices` + собственный
`ITextHost2`), причём windowless умеет рисовать и через GDI (`TxDraw`), и через Direct2D/DirectWrite (`TxDrawD2D`).

**TL;DR**

* Лучший вариант `cpp-richedit-wl-mt`: **медиана t_content 82 / 93 / 97 мс** (small / medium / large) при
  калибровочном полу `baseline-win32` 104 / 96 / 92 мс в том же прогоне (машина была нагружена параллельными
  сборками — цифры грубые). Внутри процесса (от `main` до t_content) — **47–58 мс против 58–69 мс у baseline**:
  просмотрщик markdown быстрее «пустого окна с одной строкой», потому что отключает IME/TSF (см. ниже).
* Самая ценная находка для всех прототипов: **`ImmDisableIME(-1)` экономит ~20 мс на старте любого Win32-GUI**.
  Проверено на немодифицированной копии baseline: t_content 84.0 → 62.0 мс (медиана, n=15).
* Размер дистрибутива — один exe **0.26 МБ**, статический CRT, никаких DLL, кроме системных.
* Качество: заголовки, таблицы с рамками и зеброй, блоки кода с фоном, цитаты с полосой, списки/задачи, картинки
  PNG/JPEG — всё по style spec. Не вышло: скругления, цветные эмодзи, подсветка синтаксиса, ссылки без подчёркивания.
* D2D/DirectWrite-режим **достижим** (windowless + `TXTBIT_D2DDWRITE`), вариант `cpp-richedit-d2d`, 101–114 мс.
  В оконном RichEdit переключателя на D2D нет (проверено перебором всех битов стилей).

## Сборка

```
pwsh -File bench/protos/cpp-richedit/build.ps1
```

Скрипт с нуля собирает `out/windowed/fastmd-richedit.exe` (оконный RichEdit) и
`out/windowless/fastmd-richedit-wl.exe` (windowless; режим рендера выбирается флагом). Манифест (`app.manifest`):
PerMonitorV2, supportedOS Win10+. Импорт: `user32, gdi32, imm32, dwmapi, kernel32` (+ `d2d1`, `dwrite` отложенно).

## Как это устроено

1. **`main`**: `ImmDisableIME(-1)` (просмотрщику не нужен ввод текста), запуск рабочего потока.
2. **Рабочий поток**: `ReadFile` → md4c → RTF (`md2rtf.cpp`). md4c сначала размечает блоки всего документа
   (на 3.7 МБ это ~4.5 мс), затем колбэки. Генератор оценивает высоту вёрстки (таблица реальных GDI-ширин символов
   Segoe UI Variable) и на границе верхнеуровневого блока, где оценка превысила 1400 px (≈1.75 экрана), отдаёт
   **первый кусок** RTF (заголовок + префикс + `}`) — дальше документ генерируется параллельно (large: весь RTF 25 МБ
   готов через ~45 мс после `main`).
3. **Хост RichEdit** стримит первый кусок (`EM_STREAMIN`, `SF_RTF`) и рисует первый кадр. Это разрешённая
   PROTOCOL §3 техника «сначала первый экран»; проверено скриншотами, что первый кусок полностью закрывает viewport
   (`shots/firstchunk-medium.png`, `shots/firstchunk-large.png`; для medium первый кадр попиксельно совпадает с
   финальным).
4. **t_content**: после `EndPaint`/`EndDraw` первого кадра с контентом + `DwmFlush()` (хелпер `fastmd_bench.h`).
   В оконном варианте — сабклассинг `WM_PAINT` самого RichEdit.
5. **Фаза 2** (после t_content, в bench-режиме не выполняется): весь документ.
   * `cpp-richedit-wl-mt`: вспомогательный поток создаёт **второй** экземпляр text services, заливает в него весь RTF
     (large: ~0.9 с) и отдаёт UI-потоку, который просто подменяет указатель, сохраняя позицию прокрутки. UI всё это
     время отзывчив (`shots/scroll-wlmt-bg-*.png`).
   * оконный вариант: одна полная перезаливка на UI-потоке (medium ~40 мс, large ~0.9 с — на это время UI занят).

### Как RTF изображает GitHub-стиль (что реально рисует msftedit)

Проверено пробами (`probe/`, скриншоты `probe/probe1.png` … `probe9c.png`):

| Приём CSS | Что сделано в RTF | Почему |
|---|---|---|
| фон блока кода, отступ 16 px | таблица 1×1: `\clcbpat` + `\trgaph240` + `\sb240\sa240` в ячейке | заливка абзаца `\cbpat` и рамки абзаца `\brdrX` **парсятся, но не рисуются**; заливка/рамки ячеек рисуются |
| 1 px линия под h1/h2 | таблица 1×1 с нижней рамкой `#d1d9e0`, остальные рамки белые | та же причина; таблица без рамок рисует серую сетку, поэтому «невидимые» рамки = цвет фона |
| полоса цитаты 4 px | таблица 1×1 с левой рамкой `\brdrw60` | — |
| `<hr>` 2 px | пустая таблица с верхней рамкой `\brdrw30` | строка с `\trrh`+заливкой не видна |
| line-height 1.6 | точный интервал `\sl-360` (24 px) | `\slmult1` умножает на *естественную* высоту строки шрифта (~1.33 em) |
| отступы между блоками (margin collapse) | отдельные «spacer»-абзацы точной высоты | фон символов (`\highlight`, inline code) закрашивает **всю** строку вместе с `\sb` |
| padding ячеек 6/13 | `\trgaph195` + `\trrh` (мин. высота) + `\clvertalc` | `\trpaddt/b` не работают, `\sb/\sa` в ячейке раздувают фон inline code |
| ширины колонок (max-content) | оценка по таблице GDI-ширин символов, пропорциональное сжатие до 796 px | в RTF-таблицах RichEdit нет auto-layout |
| semibold 600 | отдельное семейство `Segoe UI Variable Text Semibold` (GDI видит именованные экземпляры variable-шрифта) | `\b` даёт 700 |
| ссылки | `{\field{\*\fldinst HYPERLINK "url"}{\fldrslt{\cf3 …}}}`, клик → `EN_LINK` → `ShellExecuteW` (shell32 грузится лениво) | подчёркивание RichEdit рисует всегда |
| чекбоксы задач | глифы ☑/☐ (Segoe UI Symbol) | — |
| картинки | `\pict\pngblip`/`\jpegblip`, `\picw` в HIMETRIC, масштаб до ширины колонки | **грузятся только если контрол НЕ read-only во время `EM_STREAMIN`** (иначе молча выбрасываются; `EM_INSERTIMAGE` возвращает `E_ACCESSDENIED`) |

## Варианты (proto.json)

| id | exe / флаги | Что это |
|---|---|---|
| **`cpp-richedit-wl-mt`** (лучший) | `windowless/fastmd-richedit-wl.exe --render=gdi --ts-thread` | windowless RichEdit, GDI `TxDraw` в memory DC + `BitBlt`. Text services создаются и первый кусок стримится **во вспомогательном потоке**, пока UI-поток создаёт и показывает (пока белое) окно; затем передача владения UI-потоку. Фаза 2 — фоновая загрузка во второй экземпляр и подмена. |
| `cpp-richedit` | `windowed/fastmd-richedit.exe` | классический дочерний `RICHEDIT50W` (путь «inbox control» из задания); md4c в рабочем потоке, первый кусок, `ImmDisableIME`, read-only через фильтрацию ввода (без `EM_SETREADONLY`), фокус после первого кадра. |
| `cpp-richedit-d2d` | `windowless/... --render=d2d-sw --ts-thread --warm-d2d` | windowless + `TXTBIT_D2DDWRITE`, `ITextServices2::TxDrawD2D` в **программный** `ID2D1DCRenderTarget`; третий поток заранее создаёт D2D-фабрику/RT и прогревает общую DirectWrite-фабрику. |
| `cpp-richedit-full` | `windowed/... --full` | оконный контрол, **весь** документ стримится до первой отрисовки — показывает цену наивного подхода (large: 1.1 с). |

Остальные флаги (для экспериментов, см. `src/common.h`): `--render=d2d` (аппаратный `ID2D1HwndRenderTarget`),
`--ime` (не отключать IME), `--ro-style` (классический `ES_READONLY` + `EM_SETREADONLY`), `--early-focus`,
`--no-advtypo`, `--serial`, `--first-px=N`, `--chunk=N` (фаза 2 кусками через `SFF_SELECTION`), `--prerender`.

Разбивка оконного варианта (CPU): создание главного окна ~11 мс, создание `RICHEDIT50W` ~8.6 мс,
`EM_STREAMIN` первого куска medium ~9.2 мс (двухстрочный документ — 1.8 мс; CJK-фолбэк шрифтов +2.2 мс, эмодзи
+0.8 мс, Cascadia/таблица — десятые доли), `ShowWindow` ~5–6 мс, отрисовка ~3 мс. Весь UI-поток для
двухстрочного документа — ~28 мс CPU, для medium — ~36 мс: основная цена — окна и инициализация RichEdit, а не
объём текста.
Windowless text services дешевле окна (5–7 мс против 8.6), `EM_STREAMIN` в D2D-режиме дешевле (≈5 мс: шрифты
реализуются позже в DirectWrite). Аппаратный D2D тратит ~180 мс CPU на создание D3D-устройства (загрузка
драйвера RTX 5070) — для «пули» это приговор; программный DC-RT стоит ~14–19 мс (WARP-растеризатор), и его можно
спрятать в параллельный поток.

Параллелизм работает хуже, чем обещают такты: `CreateTextServices` в потоке-помощнике идёт ~25–34 мс «стенных»
при ~6 мс CPU — конкурирует с созданием окна на UI-потоке за общие блокировки USER/GDI. Но итог всё равно
−12 мс к t_content (A/B: 78.8 против 94.7 мс).

### Большие документы

* md4c + генерация RTF 3.7 МБ md → 25.3 МБ RTF: ~45 мс (рабочий поток, параллельно с UI).
* Размер RTF: small 3.4 КБ → 34 КБ, medium 53 КБ → 396 КБ, large 3.7 МБ → 25.3 МБ (каждый не-ASCII символ —
  `\uNNNN?`, плюс разметка таблиц).
* Полная загрузка large в RichEdit: ~0.9–1.1 с (`EM_STREAMIN` одним куском линеен).
* **Ловушка**: дописывание кусками в конец (`EM_EXSETSEL` в конец + `EM_STREAMIN|SFF_SELECTION`) после ~300 тыс.
  символов в документе становится O(кусок × документ): 256 КБ-кусок при 320 тыс. символов — 0.54 с, при 845 тыс. —
  1.4 с; 2 МБ-кусок при 440 тыс. — 7 с. Поэтому фаза 2 — одна полная заливка (или фоновый второй экземпляр).
* UTF-8 RTF (`SF_USECODEPAGE | CP_UTF8<<16`, сырые байты вместо `\u`) RichEdit принимает, текст идентичен,
  но **медленнее**: large 2.5 с против 0.96 с, medium 144 против 86 мс; RTF меньше всего на 15 %.
* RichEdit верстает большой документ лениво (фоновый пересчёт по таймеру), поэтому ползунок прокрутки «растёт», а
  `SB_BOTTOM` доходит только до уже свёрстанного; End/Home сделаны через каретку + `EM_SCROLLCARET`
  (`shots/end_large.png`).

## D2D/DirectWrite: исследование

* **Оконный `RICHEDIT50W` рисует только через GDI/Uniscribe.** Проба `probe/probe_d2dswitch.cpp` в отдельном
  процессе на каждый бит перебрала все 32 бита `EM_SETEDITSTYLEEX`, `EM_SETEDITSTYLE` и `EM_SETTYPOGRAPHYOPTIONS`
  на видимом окне: ни один не загрузил `d2d1.dll`/`dwrite.dll` (msftedit грузит их отложенно — это надёжный
  индикатор). В UTF-16-строках `msftedit.dll` нет другого имени класса окна, кроме `RICHEDIT50W` (классы с D2D в
  имени, насколько известно, есть только в офисной `riched20.dll` — её в системе нет, не проверял).
* **Windowless путь работает с первой попытки**: свой `ITextHost2`, в `TxGetPropertyBits` бит `TXTBIT_D2DDWRITE`,
  отрисовка `ITextServices2::TxDrawD2D(rt, &bounds, NULL, TXTVIEW_ACTIVE)`; `CreateTextServices` и
  `IID_ITextServices2/IID_ITextHost2` берутся экспортом из `msftedit.dll`. Хост — ~250 строк (`src/main_wl.cpp`).
  Судя по строкам `Windows.UI.Text.RichEditTextDocument` в `msftedit.dll`, этим же движком пользуется XAML
  `RichEditBox`.
* Качество D2D: DirectWrite, дробные кегли, ClearType в DC-RT; визуально почти как GDI (`shots/cmp_gdi_d2d.png`).
  Цветных эмодзи нет и там.
* Скорость: программный RT + прогрев в отдельном потоке — 101–114 мс; аппаратный — ~275–310 мс.

## Ловушки, на которые наступил

1. Заливка/рамки **абзацев** не рисуются → всё «блочное» сделано таблицами; таблица без рамок рисует серую сетку.
2. Фон символов закрашивает весь line box вместе с `\sb` → отступы вынесены в spacer-абзацы.
3. `\slmult` считает от высоты строки шрифта, а не от кегля → только точный интервал.
4. Картинки молча не загружаются в read-only контрол; а каждый переход `EM_SETREADONLY` на свежем контроле стоит
   5–10 мс CPU → контрол остаётся «редактируемым», а редактирование отфильтровано (WM_CHAR, Del/Backspace/Enter,
   Ctrl+V/X/Z/Y и форматные хоткеи, `WM_PASTE/CUT/CLEAR/UNDO`, `ES_NOOLEDRAGDROP`, IME выключен; в windowless
   хосту просто не передаются эти сообщения).
5. Лимит текста RichEdit по умолчанию 32 K символов → `EM_EXLIMITTEXT`.
6. Инициализация IME/TSF (~20 мс) при создании окна/активации/фокусе → `ImmDisableIME(-1)`.
   Обратная сторона: в процессе не будет IME (для будущего поля поиска с CJK-вводом — отдельный поток/окно).
7. Дописывание кусками — квадратичное (см. выше).
8. Windowless из двух потоков: пока помощник работает с text services, хост не должен трогать окно
   (кросс-поточный `SendMessage` в UI-поток, ждущий передачи, = дедлок) и должен отказывать в `TxSetTimer`;
   поток-помощник остаётся жить (TLS-кэши RichEdit).
9. Свой баг, найденный и исправленный: двойной `DwmFlush` (профилировочный + протокольный) добавлял до кадра к
   t_content оконного варианта.
10. RichEdit нельзя попросить рисовать ссылки без подчёркивания и скругления фона.

## Идеи дальнейшего ускорения

* **`ImmDisableIME(-1)` — всем прототипам** (−20 мс на baseline). Для Win32/D2D/Rust-прототипов с собственным
  окном это одна строка; для managed/XAML-стеков эффект не проверял.
* Создавать окно сразу `WS_VISIBLE` и/или показывать его ещё раньше (сейчас пустое окно показывается ~+39 мс).
* Уменьшить конкуренцию потоков за USER/GDI (например, помощник сначала делает CPU-работу, а `CreateTextServices` —
  когда UI уже создал окно); на простаивающей машине эффект будет меньше, чем под нагрузкой.
* Меньший первый кусок (`--first-px=900` −1 мс CPU) с проверкой покрытия через `EM_POSFROMCHAR`; не тянуть в
  первый кусок картинки ниже первого экрана (декодер WIC +10–15 мс).
* `-resident`-вариант (процесс с уже созданным RichEdit + передача пути) — не делал; по разбивке выше в резидентном
  процессе остались бы только стрим первого куска, отрисовка и `DwmFlush` (оценка, не измерение: ~20–30 мс плюс
  запуск лаунчера).
* Подсветка синтаксиса — дёшево, цветами в RTF из простого лексера (на старт почти не влияет).

## Оценка трудозатрат до продукта

Сделать из прототипа приличный v1 на этом стеке: **~3–5 недель** одного Win32/C++-разработчика: открытие файлов,
drag&drop, перечитывание при изменении, поиск (`EM_FINDTEXTEX`), масштаб (`EM_SETZOOM`), тёмная тема (другая палитра
в генераторе RTF), печать (у RichEdit есть `EM_FORMATRANGE`), оглавление, подсветка синтаксиса (~1 неделя),
проверка на 125–200 % DPI и смене DPI, ассоциация файлов/инсталлятор. Потолок качества ограничен RichEdit:
скругления, цветные эмодзи, точный CSS-лейаут таблиц, горизонтальная прокрутка кода, `text-decoration: none` —
недостижимы без перехода на собственный рендер (DirectWrite) — т.е. уже другой прототип (cpp-d2d).

### Честность t_content — вывод: честно

* **Сборка.** `build.ps1` пересобран с нуля (два раза: до и после правок): `/O2 /MT /GS- /GL /DNDEBUG` + `/LTCG
  /OPT:REF,ICF`. `dumpbin /dependents`: только `USER32, GDI32, dwmapi, IMM32, KERNEL32` (+ отложенно `d2d1`,
  `DWrite`), отладочных CRT нет. exe 262 / 272 КБ.
* **Метка.** Во всех трёх хостах `t_content` берётся в `fmb_content_presented_ex()` (общий
  `bench/common/fastmd_bench.h`): `DwmFlush()` → `GetSystemTimePreciseAsFileTime`. Вызов стоит сразу после `EndPaint`
  кадра с документом: оконный — после штатного `WM_PAINT` самого `RICHEDIT50W` (сабклассинг), windowless-GDI — после
  `TxDraw` в memory DC + `BitBlt` + `EndPaint`, windowless-D2D — после `TxDrawD2D` + `EndDraw` + `EndPaint`. Всё
  синхронно, раньше «кадр готов» ничего не отмечается.
* **Первый экран первым.** До `t_content` в RichEdit загружен только первый кусок RTF (оценка высоты ≥ 1400 px при
  окне 800 px) — это разрешённая §3 техника. Проверил, что кусок действительно закрывает окно: оконный вариант с
  `FASTMD_NO_MORE=1` (фаза 2 не выполняется) — `shots/audit2-firstchunk-windowed-{medium,large}.png`; для medium
  кадр из одного первого куска попиксельно совпадает с кадром всего документа (отличаются 3 пикселя каретки).
  wl-mt на large со `--settle 0` (до фоновой подмены, которая наступает через ~1 с) —
  `shots/audit2-firstchunk-wlmt-large-settle0.png`: экран заполнен целиком.
* **Нечестных приёмов нет.** Резидентного процесса нет, кэшей на диске нет (файлы пишутся только по отладочным
  `FASTMD_DUMP_*`/`FASTMD_TRACE`/`FASTMD_PROF`, которые харнесс не ставит), `--prerender` в `proto.json` не
  используется. В бинарник не зашито ничего из корпуса: единственная таблица (`kAdv`) — ширины глифов шрифта Segoe UI
  Variable, не текст корпуса. `tests/slice*.md` — лишь входные файлы для ручной проверки, в сборку не входят.
  `ImmDisableIME(-1)` — легитимный приём для просмотрщика (обратная сторона описана в «Ловушках», п. 6).

### Что изменено (минимально) и почему

1. **`src/main_wl.cpp`: фаза 2 (фоновая загрузка всего документа, `bg_load_full`) теперь стартует только после
   первого показанного кадра** (событие `g_ev_presented` ставится в `on_first_frame()` после `t_content`; поток-помощник
   ждёт его). Раньше в обычном режиме (без `FASTMD_BENCH_OUT` или с `FASTMD_BENCH_EXIT=0`) второй экземпляр text
   services создавался и заливался **параллельно с первой отрисовкой**, а в режиме замера (`EXIT=1`) — не запускался
   вовсе. То есть замер мерил не совсем тот путь, что видит пользователь. Первый A/B показал +13 мс (medium) /
   +30 мс (large) в обычном режиме, но повторный A/B с чередованием порядка (старый бинарник vs новый, оба режима,
   n=8, внутрипроцессный интервал `t_content − main`) разницы выше шума не подтвердил: старый — large 58.6 (EXIT=1)
   против 55.4 (EXIT=0), medium 46.8 против 52.0 мс; новый — large 57.5 / 53.8, medium 51.6 / 51.8 мс. Первое
   расхождение, видимо, было эффектом фиксированного порядка запусков. Правка оставлена как страховка: теперь до
   `t_content` обычный режим по построению делает ровно ту же работу, что и режим замера. **Путь, который мерит
   харнесс, не изменился** (добавились только `CreateEventW` при старте и `SetEvent` уже после `t_content`).
   Пункт 5 раздела «Как это устроено» для wl-mt надо читать так: второй экземпляр грузится *после* первого кадра.
2. **`src/main_wl.cpp`, D2D-режим: `t_window` ставился на кадре с контентом**, а не на первом (белом) кадре окна —
   для `cpp-richedit-d2d` `window_ms` совпадал с меткой `painted`. Добавлен `fmb_window_shown()` после `EndPaint`
   каждого D2D-кадра. На `t_content` не влияет; теперь `window_ms` d2d ≈ `shown_blank` (131.4 против 151.5 мс в
   проверке выше).

`proto.json` не менялся: все четыре варианта рабочие и осмысленные.
