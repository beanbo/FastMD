## 0. Коротко (TL;DR)

1. **Все популярные ридеры/редакторы открываются за 1–6 с** [замер, medium.md 53 KB, «визуально готово»]:
   Typora 1.14.10 ≈ **1.1 с** до 50 % кадра и 1.7 с до полной готовности; MarkText 0.20-rc.4 ≈ **3.8 с**;
   Markdown Monster 4.5.3 ≈ **4.5 с** до 50 % кадра; предпросмотр PowerToys в панели Проводника ≈ **0.6 / 1.4 с**.
   Это WebView2/Electron. Нативные новички не быстрее: Inlyne (Rust + wgpu) ≈ **1.2 с**, Ferrite (Rust + egui) ≈ **1.3 с**,
   почти всё уходит на инициализацию GPU. Калибровочный Win32-«пол» на этой машине: 0.09–0.12 с.
   **Ниша «открылось за ≤ 250 мс и выглядит хорошо» на Windows сейчас пустая.**
2. **Большие файлы — слабое место всех.** На large.md (3.7 MB) Typora показывает «Файл слишком большой для рендеринга
   в Typora». Ferrite не показал окно за 30 с (29 с CPU). Inlyne справился за 3.6 с и 940 MB commit [замер].
   Нужно рендерить сначала первый экран, остальное потом.
3. **Mermaid и формулы нужны редко** [замер, 3 405 уникальных .md из 4 корпусов]: 0.3–1.8 % документов.
   Математика — 0–0.6 %. Значит, веб-движок нужен ~2 % открытий. Остальные 98 % можно рендерить нативно,
   без платы за Chromium.
4. **Но «нативный» рендер обязан уметь больше, чем кажется** [замер, топ-500 README на GitHub]:
   - в 76 % есть сырой HTML (`<img>` 70 %, `<p align>` 45 %, `<br>` 40 %, `<picture>`+`<source media=prefers-color-scheme>` 20 %, `<details>` 19 %);
   - в 85 % есть удалённые картинки, в 69 % — SVG (бейджи shields.io с `<text>`), а у 80 % README
     удалённая картинка стоит **в первых 30 строках**, то есть в первом экране;
   - GitHub Alerts `> [!NOTE]` — в 18 % README и в 39–46 % документации (VS Code docs, Obsidian Help);
   - относительные ссылки на .md — 60–86 %, якоря `#…` — 35 %.
   **Direct2D SVG не рисует `<text>`** (по документации Microsoft), поэтому бейджи потребуют lunasvg или resvg.
5. **Гибрид — правильная архитектура.** Нативный первый кадр, веб-движок лениво и только если есть `mermaid` или `$$`.
   Цена «богатого режима» [замер, Chromium 153 = WebView2 153]:
   Mermaid 12 — 196 мс на исполнение 5.6 MB JS и ~250 мс на первую диаграмму;
   KaTeX 0.18.7 — 11 мс + 19 мс на 50 формул + ~100 мс на вёрстку и шрифты;
   Temml (MathML) — ещё легче;
   **MathJax 4 — ~1 с на 50 формул, не брать**.
   Плюс ~285 мс на создание контроллера WebView2 (отчёт 02).
   Альтернатива без браузера: **mmdr** (Rust, нативный Mermaid) — 1.7 мс на sequence, 110 мс на flowchart
   из 12 узлов [замер], 23 типа диаграмм, качество чуть хуже эталона.
6. **Анимация открытия окна в DWM съедает ~200 мс воспринимаемой скорости** [замер, экранная съёмка 60 Гц].
   С анимацией окно полностью видно через 291 мс, без неё — через 85 мс.
   `DWMWA_TRANSITIONS_FORCEDISABLED` убирает эту разницу. `t_content` в harness её **не видит**: она за `DwmFlush` (§11).
7. **Mica и тёмный заголовок бесплатны** [замер]: plain 113 / dark 108 / mica 108 / mica+dark 105 мс (медианы, n=12).
   Разница в пределах шума. Стильный Windows 11 не мешает скорости.
8. **Шрифты для стиля уже есть в ОС** [проверено на машине]: Segoe UI Variable (оси wght 300–700 и opsz 5–36),
   **Cascadia Code/Mono (входят в систему)**, Segoe UI Emoji (цветные), Segoe Fluent Icons, Sitka VF (serif-вариант),
   Cambria Math (для MathML), CJK: Yu Gothic UI, Microsoft YaHei UI, Malgun Gothic. Шрифты возить с собой не нужно.
9. **Ширина строки в текущем style spec слишком большая** [замер, метрики Segoe UI Variable]:
   колонка 860 − 2×32 = 796 DIP при 15 px даёт ~**119** латинских или ~**102** кириллических символа в строке.
   Норма 45–90. Рекомендация для продукта: тело 16 DIP, текст до 680 DIP (как у Bear, ~86 кир. / 97 лат.),
   таблицы, код и картинки могут выходить шире.
10. **Must-have v1** (§5): GFM, подсветка кода, светлая/тёмная/авто тема, зум, Ctrl+F, выделение и копирование,
    кнопка «копировать код», оглавление, навигация по якорям и относительным .md (с «Назад»),
    локальные и удалённые картинки с SVG, подмножество HTML, GitHub Alerts, скрытие front matter, emoji-shortcodes,
    live reload, «Открыть в редакторе», ассоциация файлов, drag-and-drop, недавние файлы через Jump List.
    **Позже:** Mermaid и формулы (ленивый движок), печать и PDF, обработчик панели просмотра Проводника
    (там у PowerToys 0.6–1.4 с — хороший шанс выделиться), вкладки.

### 2.2 Что видно на скриншотах [замер]

Файлы `shots/*.png`. Главные наблюдения по «стильности»:

- **Typora**: ровная GitHub-подобная вёрстка, но заголовки и текст разными гарнитурами. Меню занимает строку,
  в статус-баре плашка «НЕТ РЕГИСТРАЦИИ».
- **MarkText**: минимальный хром, узкая колонка по центру (~640 px), тёмная тема из системы. Выглядит лучше всех «из коробки».
- **Markdown Monster**: 3 панели, 2 тулбара. Для чтения визуальный шум.
- **PowerToys Preview**: аккуратно, но жёлтая плашка «Некоторые изображения были заблокированы…» сверху.
- **Inlyne**: хорошая типографика текста, но гигантские отступы списков и путь `\\?\…` в заголовке окна.
- **Ferrite**: нет вертикального ритма (заголовок прилипает к абзацу), текст от края окна, эмодзи — тофу-подобные контуры.

Вывод: **хороший вкус даёт GitHub-подобная вёрстка + узкая колонка + минимальный хром.**
Скорость ни у кого из этих приложений не лучше ~1 с.

1. **Разрыв между «окно появилось» и «контент готов»** — главный UX-дефект WebView2-приложений.

2. **Нативный — не значит быстрый.** Inlyne и Ferrite тратят ~1 с на инициализацию GPU (wgpu/glow) и вёрстку
   всего документа. То же видно в предварительных прогонах агента rust-gpu в `bench/results`: egui ≈ 1.07 с.

   а это важно для первого впечатления.
4. **Памяти берут все много**: 230–570 MB commit на документ 53 KB. Для ридера разумный бюджет ≤ 50–80 MB.

### 6.3 Ограничение нативной графики: SVG

Direct2D `ID2D1SvgDocument` поддерживает только `circle, clipPath, defs, desc, ellipse, g, image(base64), line,
linearGradient, path, polygon, polyline, radialGradient, rect, stop, svg, title, use`.
**Нет `<text>`, `<style>`, `mask`, `filter`, единиц `em`/`ex`** (Microsoft Learn).
Значит, бейджи shields.io (текст в SVG), mermaid-SVG и логотипы с текстом в Direct2D выйдут без текста.
Нужен **lunasvg 3.x** (C++, с 3.0 умеет текст с системными шрифтами, есть в vcpkg) или **resvg** (Rust, эталон по точности).
Решение не зависит от выбора UI-стека и нужно в v1.

## 7. Гибрид: мгновенный нативный первый кадр + ленивый веб-движок

### 7.1 Временная шкала (целевая)

```
t=0        double-click → CreateProcess (Defender ~20–35 мс; пол Win32 ≈ 90 мс до t_content)
~40 мс     main: mmap файла; быстрый скан «нужен ли rich-режим» (```mermaid, $$, \begin{) — микросекунды
~60 мс     окно создано: тема, Mica и dark caption выставлены ДО ShowWindow (бесплатно, §8.4),
           DWMWA_TRANSITIONS_FORCEDISABLED (–200 мс воспринимаемого времени, §8.5)
~150–250   ПЕРВЫЙ КАДР: вёрстка только видимого экрана. Картинки — плейсхолдеры с зарезервированным местом,
           mermaid/math — плейсхолдер «диаграмма…» (или исходник в стиле кода)
после кадра (idle): вёрстка остального → TOC → индекс поиска → подсветка видимых блоков →
           декодирование картинок (WIC) → HTTP-картинки из кэша/сети → watcher → Jump List
только если нужно (~2 % документов):
+0         создать WebView2 environment (дёшево) и controller (~285–600 мс) НЕВИДИМО
+~200      исполнить mermaid.min.js / katex.min.js
+~35–250   каждая диаграмма/формулы → SVG/HTML → подставить в документ
```

### 7.2 Три способа «подставить»

| Вариант | Как | Плюсы | Минусы / риски |
|---|---|---|---|
| **A. Веб как вычислитель** (рекомендуется) | Скрытый WebView2 получает исходник → `mermaid.render()` → **SVG-строка** через `postMessage` → нативный рендер через lunasvg/resvg прямо в документ. Для формул — KaTeX/Temml → MathML/HTML → **снимок** (`CapturePreview` в PNG) | Документ целиком нативный: один скролл, один поиск, одна тема. Нет airspace-проблем | Mermaid по умолчанию кладёт в SVG `foreignObject` (HTML-подписи): нужно `htmlLabels:false`. Нужно проверить `getBBox` в скрытом окне (у скрытого окна нет кадров, отчёт 02). Снимки формул не масштабируются при зуме, их надо перерендерить |
| B. Замена всего документа | Когда WebView2 готов, отрисовать весь документ в нём тем же `style.css` и подменить нативный вид, сохранив позицию прокрутки | Просто. Полная точность (CSS, `<video>`, …) | Видимый «скачок» при разных метриках; +100–200 MB; поиск и выделение переключаются между движками |
| C. Без браузера | mmdr (Rust, через C ABI или отдельный процесс) для Mermaid; MicroTeX или своя вёрстка для формул | Ни одного Chromium-процесса. Mermaid за 2–110 мс | Точность mmdr (0.3.x, «may not yet match mermaid-cli»). Проект MicroTeX не обновлялся с 2024 |

**Рекомендация.** v1: Mermaid и формулы показываются как красиво оформленный исходник с бейджем
«диаграмма» / «формула». Это честно и мгновенно, а исходник Mermaid читается и сам по себе.
v1.x: вариант **A** (ленивый WebView2 как вычислитель) и параллельно оценка mmdr как варианта **C** для Mermaid.
Режим **B** оставить как fallback «Открыть в полном веб-режиме» для документов с тяжёлым HTML.

### 7.3 Связь со стратегией «резидента»

Если оркестратор выберет вариант `-resident` (отчёт 02: общий browser-процесс даёт −45–50 % к WebView2),
то для rich-документов можно держать один прогретый WebView2-процесс. Для обычных документов это бессмысленно:
нативный путь и так укладывается в первый кадр.

### 8.4 Материалы и хром окна [замер]

- **Mica / Mica Alt, тёмный заголовок: стоимость старта = 0** в пределах шума.
  `t_content`, медианы n=12: plain 112.9 · dark 107.6 · mica 108.2 · mica+dark 104.6 мс.
  `DwmSetWindowAttribute` занимает < 0.5 мс (метки `window_created` → `dwm_attrs_set`).
- Правила Microsoft: Mica — только базовый слой долгоживущего окна (заголовок, сайдбар).
  Контент — на отдельном слое (`LayerFillColorDefault`). Mica сэмплирует обои один раз.
  При экономии батареи, выключенной прозрачности или неактивном окне отдаёт сплошной цвет.
  Для ридера: **Mica в заголовке и TOC-сайдбаре, документ на сплошном фоне** (читаемость).
- **Без белой вспышки:** фон окна в цвете темы (свой `WM_ERASEBKGND`/`WM_PAINT`),
  `DWMWA_USE_IMMERSIVE_DARK_MODE` до `ShowWindow` (иначе светлый заголовок мигнёт),
  для WebView2 — `DefaultBackgroundColor` или переменная `WEBVIEW2_DEFAULT_BACKGROUND_COLOR`.
- Минимальный хром: без тулбара по умолчанию. Заголовок окна = имя файла. Кнопки TOC / поиск / тема / «⋯» в заголовке (Fluent Icons).

### 8.5 Движение [замер]

Открытие окна по экрану (BitBlt рабочего стола ≈ 60 Гц, медианы n=10, `mica_test --mode=plain`):

| | окно видно (флаг) | 50 % на экране | 90 % на экране | Полностью на экране |
|---|---:|---:|---:|---:|
| С анимацией DWM (по умолчанию) | 66 мс | 154 мс | 228 мс | **291 мс** |
| `DWMWA_TRANSITIONS_FORCEDISABLED` | 62 мс | 85 мс | 85 мс | **85 мс** |

Системная анимация открытия (масштаб + прозрачность) **добавляет ~200 мс** до полностью видимого документа.
Для «пули» её стоит выключить. Возможно, сделать это настройкой («мгновенное открытие», по умолчанию вкл.).
Внутри приложения: никаких анимаций при открытии. Плавная прокрутка колесом ~100–150 мс.
Уважать «Эффекты анимации = выкл» (`SPI_GETCLIENTAREAANIMATION`).

## 10. Выводы для FastMD

### 10.1 Рекомендации

1. **Позиционирование:** «Ридер Markdown, который открывается быстрее Notepad и выглядит как GitHub в Windows 11».
   Конкуренты: 1–6 с (Electron/WebView2) или ~1.2–1.3 с (нативные GPU-новички) [замер].
   Цель FastMD: **≤ 250 мс до первого экрана** на medium, **≤ 400 мс** на large (первый экран сначала).
2. **Архитектура: нативный рендер + ленивое обогащение.** Веб-движок не входит в критический путь ни для одного документа.
   Для ~2 % документов с Mermaid или формулами он поднимается после первого кадра (вариант A из §7.2).
   Для Mermaid дополнительно оценить нативный mmdr.
3. **Объём нативного рендера v1** — по данным §4: GFM + alerts + footnotes + front matter + emoji-shortcodes +
   подмножество HTML (§4.3) + картинки (WIC) + **SVG с текстом (lunasvg/resvg, не D2D)** +
   асинхронные удалённые картинки с кэшем + цветные эмодзи + CJK fallback + подсветка кода.
   Это обязательная часть, а не «nice to have»: без неё README с GitHub выглядит сломанным.
4. **Парсер:** md4c master (2026) уже умеет `MD_FLAG_FOOTNOTES`, `MD_FLAG_ADMONITIONS`, `MD_FLAG_LATEXMATHSPANS`,
   `MD_FLAG_WIKILINKS`, `MD_FLAG_HIGHLIGHT`. Последний тег `release-0.5.3` — нужно фиксировать коммит.
5. **Стиль:** Segoe UI Variable (opsz!), Cascadia Mono, палитры GitHub light/dark, тема по системе
   (у пользователя тёмная), тело 16 DIP, колонка до 680 DIP с breakout, Mica только в заголовке и сайдбаре,
   без белой вспышки, **без анимации открытия** (−200 мс воспринимаемого времени).
6. **Функции v1 (§5):** поиск, TOC, зум, выделение и копирование, копирование кода, якоря, навигация по .md с «Назад»,
   live reload с сохранением прокрутки, «Открыть в редакторе», ассоциация, drag-and-drop, Jump List.
   Всё, что не нужно для первого кадра, инициализировать **после** него.
7. **v2-козырь:** нативный preview handler для панели Проводника (PowerToys: 0.6–1.4 с, блокирует картинки;
   #45267 и #46087 показывают спрос).

## 11. Замечания к harness и протоколу (для оркестратора)

1. **`t_content` не видит анимацию открытия DWM** [замер, §8.5]. `DwmFlush()` возвращается, когда кадр скомпонован,
   но на экране окно ещё ~200 мс «вырастает». Если один прототип выставит `DWMWA_TRANSITIONS_FORCEDISABLED`,
   а другие нет, по `t_content` это не будет видно, а по ощущению разница ~200 мс.
   Предлагаю: (а) договориться, что все прототипы оставляют анимацию по умолчанию (для сравнимости);
   (б) добавить в harness опциональную метрику «на экране» (BitBlt рабочего стола в прямоугольнике окна,
   как в `mica/run_transition.py`).
2. **Режим `external-title` меряет только появление окна**, а не контент. У Markdown Monster окно появляется за 0.5 с,
   а контент за ~4.5 с [замер]. Для сторонних приложений стоит использовать визуальную шкалу
   (`measure_apps.py`: PrintWindow-кадры → p50/VC). Скрипт импортирует `bench.py` и не требует правок harness.
3. Grab-частота: `PrintWindow(PW_RENDERFULLCONTENT)` для окна 1000×800 даёт ~20–40 кадров/с.
   Для точности ±15 мс на быстрых прототипах лучше BitBlt экрана (60 Гц), но окно тогда не должно быть перекрыто.
4. Подвох для CLI-замеров: **Glow 3.0 читает stdin вместо файла-аргумента, если stdin не TTY** (например, pipe).
   Отсюда «2 байта вывода» за 0.17 с. Нужно `stdin=DEVNULL`.
