## 0. Коротко (TL;DR)

1. **Разбор Markdown никогда не бывает узким местом, если парсер нативный и потоковый.**
   md4c (master 0.6.0-dev; релиз 0.5.3 так же) разбирает large.md (3.8 MB) за **10.6 мс** (342 MB/s), в HTML — за **16.2 мс**.
   pulldown-cmark 0.13.4 — за 16.8 / 19.7 мс. medium.md (53 KB) у обоих занимает **0.14–0.20 мс** [замер].
   Дальше по скорости идут cmark 98 мс, comrak 151 мс, cmark-gfm 283 мс, marked 286 мс, Markdig 304 мс, markdown-it 421 мс.
   micromark — 4.8 с. **markdown-rs растёт сверхлинейно: 16–26 с на large.md** [замер]. Эти два для FastMD не подходят.
2. **Для управляемых рантаймов важен холодный первый вызов, а не пропускная способность** [замер, medium].
   Markdig: JIT — **~55 мс** (сборка pipeline 11.5 мс + первый `ToHtml` 43 мс); ReadyToRun — ~19 мс; NativeAOT — **2 мс**.
   Node: markdown-it — `import` 26 мс + первый рендер 28 мс; marked — 9 + 28 мс; micromark — 75 + 93 мс.
3. **Соответствие спецификациям** [замер, 652 примера CommonMark 0.31.2 + 24 примера расширений GFM, нормализатор cmark].
   Если прощать чисто косметику HTML (`&quot;`, `style` вместо `align`, `<s>` вместо `<del>`), то:
   - **comrak — 652/652 и 24/24**, это единственный безупречный вариант;
   - markdown-rs и micromark — 652/652 и 23/24;
   - **md4c — 652/652 и 17/24** (релиз 0.5.3 — 18/24; в master регрессия автоссылки с точкой на конце):
     пограничные случаи autolink (4 в master, 3 в 0.5.3), 2 пограничных случая таблиц, нет tagfilter;
   - **pulldown-cmark — 652/652 и 12/24**: GFM-автоссылок (`www.…`, голые URL) **нет вообще**, 0/11;
   - cmark-gfm — 641/652, он отстаёт на версию спецификации (0.29);
   - Markdig — 651/652 и 15/24, расходится с GFM на таблицах; marked — 640/652 (ошибки в сущностях) и 22/24.
4. **Подсветка кода: нативные лексеры на 1–2 порядка быстрее грамматических движков** [замер, 7 языков].
   **Lexilla 5.5.3** (лексеры Scintilla/Notepad++): создание 7 лексеров — 0.1–0.3 мс, первый блок — < 0.2 мс, ~30 MB/s.
   Дальше: tree-sitter ~3 MB/s, но компиляция запросов стоит 4–19 мс на язык. Prism (V8) 5–7 MB/s, highlight.js 2–3 MB/s.
   syntect **0.9 MB/s** и 18–19 мс на ленивую загрузку синтаксисов. Shiki 0.16–0.36 MB/s плюс 100–150 мс инициализации.
5. **Формулы.** KaTeX — **~0.1 мс на формулу** (в V8). MathJax 3/4 — ~0.8 мс.
   В браузере **MathJax 4 с a11y-обогащением по умолчанию тратит 1.08 с на 50 формул, а без него — 70 мс** [замер].
   Нативно без JS: **RaTeX 0.1.14** (Rust, совместим с KaTeX) — **0.6–1.0 мс** на первую формулу холодным
   и **~70 мкс** на формулу дальше. Результат почти не отличается от KaTeX (`docs/ratex-vs-katex.png`) [замер].
6. **Mermaid.** `mermaid.min.js` весит 5.58 MB и исполняется **172 мс**; первая диаграмма появляется через 394 мс от старта страницы.
   **Кэш кода V8 в постоянном профиле сокращает исполнение до 36–43 мс, но только с третьего запуска** [замер].
   Нативный **mermaid-rs-renderer (mmdr) 0.3.1**: flowchart — 82–90 мс холодным и ~40 мс тёплым, sequence — 0.3 мс [замер].
7. **Большой документ упирается в раскладку и память, а не в парсер** [замер, large.md].
   DirectWrite раскладывает первые 40 блоков за **1.7 мс**, а все 101 235 блоков — за **~1.0 с** в одном потоке (0.4 с на 16 потоках).
   **Если держать все `IDWriteTextLayout` в памяти, это +1.52 GB private bytes.**
   В Chromium документ целиком даёт кадр через **1.85 с**; с `content-visibility:auto` — 0.73 с;
   с приёмом «первые 64 KB, остальное порциями» — **0.26 с**.
8. **Картинки: WIC отдаёт размеры за 0.07–0.22 мс** (первый вызов с загрузкой кодека — 6–13 мс).
   Полное декодирование 12-мегапиксельного JPEG занимает 70–80 мс, PNG 4000×3000 — ~120 мс [замер].
   Отсюда правило: размеры синхронно, пиксели асинхронно и только для видимого.
9. **Ни один массовый ридер под Windows не открывает файл быстрее ~0.6–1 с** [отчёт 06, замер]: Typora 1.7 с,
   MarkText 3.8 с, Markdown Monster 4.5 с, PowerToys 0.6/1.4 с, Inlyne 1.2 с, Ferrite 1.3 с.
   Почти все они — Electron/WebView2 плюс JS-парсер (markdown-it, marked, Markdig), highlight.js или Prism, MathJax или KaTeX и mermaid.js.
10. **Рекомендация (§9):**
    - парсер **md4c** для C++ или pulldown-cmark с отдельным проходом автоссылок для Rust;
    - подсветка **Lexilla** (или tree-sitter, лениво и вне UI-потока);
    - формулы: v1 показывает исходник, v1.x рендерит через **RaTeX** в нативный display list;
    - Mermaid: v1 показывает исходник, v1.x — mmdr, fallback — скрытый WebView2;
    - большие файлы: полный разбор, раскладка только видимого, оценка высот, фоновая раскладка остального, LRU-кэш раскладок.

### 2.3 Соответствие CommonMark 0.31.2 и GFM [замер]

Что на самом деле стоит за провалами (разбор диффов через `show_fails.py`):

- **pulldown-cmark.** Все 21 «провал» CommonMark — это только `"` в тексте без экранирования в `&quot;`. HTML корректный,
  по смыслу 652/652. В GFM: таблицы расходятся лишь косметикой (`style` вместо `align`, пустой `<tbody>`).
  **Автоссылок-литералов (`www.x.org`, голый `https://…`, e-mail) нет совсем: 0/11**, в `Options` 0.13.4 такого флага нет
  (проверено по исходнику crate). Для README это заметно, ссылки там часто голые. Лечится своим проходом по `Event::Text`,
  например crate `linkify`.
- **md4c.** CommonMark — 100 %. Таблицы: `\|` внутри code span в ячейке остаётся с обратным слешем (пример 200);
  таблица, у которой число колонок в заголовке и в строке-разделителе не совпадает, принимается как таблица (203).
  Автоссылки: 4 пограничных случая — точка на конце URL, несбалансированные `))`, `&hl;`, `<` в URL.
  **Точка на конце — регрессия master**: релиз 0.5.3 пример 623 проходит (`www.commonmark.org/a.b.` → ссылка без точки),

### 2.5 Позиции в исходнике у md4c без API [замер]

`c/md4c_ptrcheck.c` проверяет, куда указывают указатели во всех текстовых колбэках md4c:

- medium: 1 946 колбэков указывают внутрь исходного буфера, 204 — вне его;
- large: 131 769 внутрь, 13 746 вне.

**Все указатели «вне» имеют тип `MD_TEXT_CODE`** — это статическая строка `"\n"` на концах строк блоков кода.
Значит, смещение любого фрагмента текста в исходнике — это просто `ptr − src`, патчить md4c не нужно.
Этого хватает для синхронизации прокрутки с редактором, для «открыть в редакторе на этой строке» и для подсветки
результатов поиска по исходнику. Позицию блока можно брать по его первому текстовому потомку.

### 3.2 Качество и цена интеграции

- **Lexilla** — лексический уровень (ключевые слова, строки, комментарии, числа, препроцессор), то есть то же, что Prism или highlight.js.
  Минус: **списки ключевых слов задаёт хост** (в SciTE — `*.properties`, в Notepad++ — `langs.model.xml`).
  Один лексер `cpp` обслуживает C, C++, C#, Java, JS и TS через разные наборы слов. Нужен свой тонкий `IDocument`
  (`TestDocument` из Lexilla — готовый образец на 300 строк) и отображение номеров стилей в цвета темы. Лицензия пермиссивная, в стиле HPND: «Permission to use, copy, modify, and distribute… without fee»
  (License.txt Lexilla/Scintilla).
- **tree-sitter** — лучшее качество (синтаксическое дерево, инъекции языков), рантайм на C, удобно из C++ и Rust.
  Минусы: мегабайты на грамматику, **компиляция запросов 4–19 мс на язык при первом использовании**
  (её надо делать лениво и не в UI-потоке) и ~3 MB/s.
- **syntect** — грамматики Sublime, как у bat и Zola, выглядит «как на GitHub». Но это самый медленный нативный вариант
  (0.9 MB/s, 18–19 мс на первое использование 7 языков). Прототип `rust-webview` подсвечивает syntect'ом
  в рабочем потоке, вне критического пути.
- **Прототипы `cpp-d2d` и `cpp-webview2` используют самописные мини-лексеры** (16 языков и ~250 строк C соответственно).
  Для прототипа это нормально, но у продукта качество и охват языков будут хуже. Lexilla — прямой апгрейд с той же стоимостью.
- **Shiki** даёт качество VS Code, но это 100–150 мс инициализации и 10–20× медленнее Prism. В путь первого кадра его брать нельзя.

### 3.3 Стратегия «видимое сначала»

На первом экране medium 1–3 блока кода по 0.2–1 KB. Отсюда:

- **Lexilla**: 0.06–0.17 мс на первый блок холодным. Подсвечивать **синхронно, до первого кадра**: тогда кадр
  сразу финальный и цвета не «прыгают».
- **tree-sitter / syntect / JS**: первый кадр рисует код моноширинным без цвета (или с цветами из кэша по хешу содержимого).
  Подсветка видимых блоков идёт в фоновом потоке сразу после кадра, затем остальных в порядке близости к viewport.
  Грамматику языка грузить при первой встрече. Результат кэшировать по (хеш блока, язык, тема).
- Для огромных файлов (1 659 блоков, 297 KB кода в large) подсветку **никогда не делать целиком заранее**:
  даже Lexilla тратит 9–13 мс, syntect — 0.3 с, Shiki — 1–2 с. Подсвечивать на границе viewport ± 1–2 экрана.

  Sequence практически совпадает по структуре.

| Диаграмма | Холодно (первый вызов в процессе) | С `fast_text_metrics` | Тепло (медиана 20) | SVG |
|---|---:|---:|---:|---:|
| flowchart, 9 узлов | **82–90 мс** | 41–48 мс | **39–41 мс** | 9.0 KB |
| sequence, 3 участника | 0.35–0.41 мс | 0.28–0.38 мс | **0.25 мс** | 7.3 KB |

Первый вызов дороже из-за инициализации метрик шрифтов; раскладка flowchart занимает ~40 мс.
Отчёт 06 мерил CLI `mmdr --timing` на flowchart из 12 узлов: 110 мс, из них 107 мс на layout.
Тестовый exe весит 5.7 MB. Библиотека умеет 23 типа диаграмм, MIT [источник].
**Для SVG с `<text>` нужен рендер SVG с текстом** — lunasvg или resvg; Direct2D `<text>` не рисует (отчёт 06).

### 5.3 Вывод по диаграммам

Mermaid есть в 0.3–1.8 % документов (отчёт 06), и **в путь первого кадра он не попадает никогда**.

- **v1:** исходник в блоке кода с бейджем «диаграмма».
- **v1.x:** mmdr в фоне → SVG → lunasvg/resvg → битмап в документ. Это 40–90 мс на flowchart вне UI-потока, Chromium не нужен.
- **Fallback для точности:** скрытый WebView2 с постоянным профилем, `mermaid.render()` → SVG-строка (вариант A из отчёта 06).
  Первые два запуска платят ~175 мс за скрипт, дальше ~40 мс.

### 7.3 Стратегия для FastMD (нативный путь)

1. **Разбирать весь файл сразу.** md4c укладывается в 11 мс на 3.8 MB, инкрементальный парсер не нужен.
   Если строить модель документа дорого, можно сначала построить префикс до безопасной границы блока (≥ 48 K символов),
   как делает `cpp-d2d`. Цена: ссылки-определения `[x]: url` в хвосте документа разрешатся только после полного разбора.
   Их надо перерисовать в фоне.
2. **Раскладывать только видимое и ± 1 экран** (~2 мс). Высоты остальных блоков **оценивать** за O(1) на блок:
   символы × средняя ширина / ширина колонки × высота строки; для картинок брать размеры из WIC.
   Прокрутка и полоса работают сразу.
3. **Уточнять высоты в фоне** пачками в пуле потоков: на large.md это 0.4–1 с. Якорем прокрутки держать блок в верхней части
   экрана, чтобы уточнение высот не сдвигало видимое.
4. **Не держать раскладки невидимых блоков.** LRU на несколько экранов, для остальных хранить только высоту и смещение.
   Разница — 1.5 GB против единиц мегабайт.
5. Индекс поиска строить по исходному тексту: смещения из md4c есть (§2.5), подсветку совпадений маппить на блоки.
6. Подсветку, картинки, формулы и диаграммы доделывать в той же очереди «видимое сначала» (§3.3, §4.3, §5.3, §6).

### 9.2 Подсветка кода

- **C++: Lexilla 5.5.3**, статически, подмножество лексеров для топ-20–30 языков (оценка ~0.2–0.5 MB по замеру 5 и 125 лексеров).
  Подсвечивать **синхронно до первого кадра**: < 0.2 мс на первый блок, ~30 MB/s. Ключевые слова взять из `.properties` SciTE,
  цвета — из GitHub-палитры в `style.css`.
- **Качество «как в IDE»** (вложенные языки, семантика) — tree-sitter, лениво по языкам, вне UI-потока, с кэшем.
  Это v2, а не v1.
- **Rust:** syntect уже стоит в `rust-webview`, но он в 30 раз медленнее Lexilla: только фон и только видимое.
  Альтернативы — tree-sitter-highlight или Lexilla через `cc`.
- **Веб-путь:** Prism (самый быстрый в V8, 58 KB) или highlight.js common (129 KB). Shiki — нет.

### 9.3 Формулы и диаграммы

- **v1:** исходник формул и Mermaid в оформленном блоке с бейджем. Ноль миллисекунд на первый кадр.
  Это покрывает 98 % документов, где их нет, и не ломает остальные 2 %.
- **v1.x, нативно, в фоне:**
  - **RaTeX** (C ABI): 70 мкс на формулу, display list → DirectWrite с TTF KaTeX (514 KB);
  - **mmdr**: 40–90 мс на flowchart → SVG → lunasvg/resvg.
  Оба — молодые проекты (0.1.x / 0.3.x): закрепить версии, прогнать на реальных корпусах (отчёт 06, §4), держать fallback.
- **Fallback точности:** скрытый WebView2 с постоянным профилем: KaTeX или Temml; MathJax только без обогащения;
  mermaid ESM или IIFE. Результат (SVG или снимок) встраивается в нативный документ.
  Кэш кода V8 даёт ~4× выигрыш со 3-го запуска.

### 9.4 Большие документы и картинки

- Разбор целиком (≤ 20 мс на 4 MB). Раскладка — **только видимое ± 1 экран** (~2 мс). Остальное — оценка высот и фоновая
  раскладка в пуле (0.4–1 с на large). **LRU раскладок** вместо хранения всех (1.5 GB → мегабайты).
- Картинки: `GetSize` синхронно (0.2 мс, место резервируется), декодирование асинхронно (20–130 мс) и только в окрестности viewport.
  Для JPEG — `IWICBitmapSourceTransform` (DCT-масштаб), кэш по (путь, mtime, ширина).
- Если выбран WebView2: первый кусок HTML 24–64 KB, остальное через `postMessage` порциями + `content-visibility:auto`.
  Кадр через 0.26 с вместо 1.85 с на large.

### 9.6 Риски

- **GFM-идентичность.** С md4c и pulldown-cmark часть документов будет рендериться не 1:1 как на GitHub: автоссылки, края таблиц.
  Нужен регрессионный набор — GFM spec плюс реальные README из корпуса отчёта 06.
- **Молодые нативные рендеры** (RaTeX 0.1, mmdr 0.3): точность и поддержка. Нужен fallback на WebView2.
- **Lexilla:** ключевые слова и цвета — наша ответственность. Качество — лексическое, без вложенных языков (JS в HTML и т. п.).
- **Раскладка реальных документов** (inline-форматирование, fallback-шрифты, эмодзи) дороже моего замера.
  Цифры §7.1 — нижняя граница.

   В master найдена регрессия автоссылки с точкой на конце (GFM, пример 623).
7. Сборка C/C++ части лаборатории теперь воспроизводима: `c/build_benches.cmd` проверен, пишет в новую папку `c/out-rebuild/`.
